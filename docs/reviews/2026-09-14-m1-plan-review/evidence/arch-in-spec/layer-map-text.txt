Fig. 1  — The two heavy lines are the boundaries a test can fail on. Everything else is
convention. L4 is filled because it is the only place an action is ever authorized: the master,
a tier-2 session over MCP, a queue write-back and a UI click all arrive at the same
authorize() . Each capability is declared once as a  ToolDef ; the
vendor-shaped formats are exporters hanging off that one registry.
The four invariants 
Each one enforced by a build, not a reviewer 
store/ owns all SQL

choice that the multi-user path can reopen without a rewrite.  D26 
enforced by test_import_boundary.py

one suite per seam 
Every seam ships one contract suite that all implementations pass, a  Fake 
included. A new provider is done when it passes the suite that already exists.

Figure 2 — why L4 exists 
One read path, not one per consumer 
The spec is explicit that it is drawn against a failure it watched happen: a prior tool grew
349 endpoints, each with its own read logic, until its architecture document no longer
described the system. The layer map's job is to make that shape impossible to reach by accident.

Figure 3 — process split 
The module map folds into two daemons 
Layers are an import rule; processes are a restart rule. The split exists for one reason: if the
control plane owns the ptys, upgrading it kills your agents.

One thing to watch 
master/ ,  web/  and  cli/  sitting as equals at L5 is the
invariant most likely to erode under implementation pressure. The first time the fleet page
wants a query that is not in the tool surface, the honest move is to add it there — not to
let  web/  reach down one layer "just this once". That is the exact edge Fig. 2 is
about.
