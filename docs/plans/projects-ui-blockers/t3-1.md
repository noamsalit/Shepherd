# T3.1 — `toolsurface/tools_projects.py`

## T3.1 · `delete_project` is **not registered**: its store verb deadlocks the writer thread · owner: router → Phase 1 remediation

**Symptom.** `writes.delete_project` calls its injected `kill(session_id)` at
`src/shepherd/store/writes.py:207`, inside the lambda `Store._write` executes on
the single writer thread **after `BEGIN IMMEDIATE`**. The shipped kill path's
first statement is itself a store write —
`src/shepherd/orchestration/lifecycle.py:126`,
`store.set_app_state(f"{KILL_RECORD_PREFIX}{session_id}", record)` — and that
docstring says the write-before-kill order is what survives a crash, so it
cannot be reordered away. `_write` enqueues and blocks on `done.wait()`, so a
`kill` that touches the store enqueues a job the blocked writer can never reach.
The writer is a daemon thread with **no timeout**, so every subsequent write in
the process hangs permanently. The coordinator reproduced it:
`DEADLOCK: delete_project did not return within 10s`.

**What was tried.** Nothing was wired. The seam was read first —
`writes.py:207` and `lifecycle.py:126` were both confirmed present at this
builder's base (`44c26cc`), which is the pre-split world — and the verb was left
unregistered on the coordinator's explicit instruction. Registering it with an
inert stub was considered and rejected: Phase 1's suite is green **only**
because every test there passes one (`kill=killed.append`,
`kill=lambda _: None`), and a callback under test is a stub under test. A
subprocess-issuing callback under an exclusive SQLite write lock is wrong even
on the runs where it does not deadlock, because it holds the lock for the
duration of N tmux kills.

**What it blocks.** Phase 3's exit criterion *"seven tools register and
freeze"*; D61's whole three-way choice; the Projects page's delete dialog
(Phase 9). `PROJECT_TOOL_NAMES` ships with **six** names, and
`test_delete_project_is_not_registered_and_the_reason_is_the_writer_thread`
asserts the absence so it lives where a consumer trips over it rather than only
in this file. That test goes red the moment the verb is wired, which is the
point: the next builder has to come back, read why, and delete it deliberately.

**What did ship, so the split's builder does not re-derive it.**
`on_running_schema()` derives the enum from `OnRunning` — never typing the three
strings, which is exactly how the plan carried `["refuse", "kill", "orphan"]`
for five revisions after `OnRunning.KILL` became `"kill_sessions"`. It carries
**no `default`**: D61's default-refuse has to be unskippable by omission, and a
schema default is a value a caller is handed without asking for it.
`test_the_on_running_enum_is_on_running_itself` reads the enum on both sides, so
it is tautological about the spelling and load-bearing about the link.

## T3.1 · three refusal conventions in `store/`, aligned on one record **at the tool surface**

`rename_project` raises `StoreError` for the reserved project and answers `None`
for a missing one; `add_repo` raises for both; `delete_project` returns a record
for both. Three shapes for one family of verbs means three error adapters at
this layer, and a consumer will eventually branch on two of them and crash on
the third. Every one of them now becomes `{"<verb>": False, "<subject>": None,
"refused": "<why>"}`. Nothing in `store/` was changed to achieve it — the
adapters are `_refused()` and two `try/except StoreError` blocks in
`tools_projects.py`.

A raised `StoreError` is not a neutral outcome here: `registry.py:69` turns any
handler exception into `GENERIC_ERROR = "request failed"`, so a guard that
raises reaches the page as a failure with no reason, and the reserved-project
refusal is precisely the case a page has to explain.

## T3.1 · `add_repo` probes git, and a path that does not probe is refused

`git_common_dir` is D48's binding key. The tool canonicalizes the path (E10 —
`store/` does no filesystem I/O), runs `probe_repo`, refuses a non-repo and
refuses a bare repo, and resolves the repo's **own root** with `repo_root` — the
same helper `bind_cwd_to_repo` uses, so a person who types a subdirectory
registers the tree rather than giving one `git_common_dir` two `repo` rows under
`ux_repo_path`.

`test_a_ui_registered_repo_binds_a_discovered_session_to_that_project` states it
end to end: registration through `invoke()`, binding through the shipped
`bind_cwd_to_repo`, and **no `git_common_dir` passed between them**. That test
also ends the inter-phase state in which every spawn was refused — until this
verb existed nothing could register a repo, so `_registered_roots` was empty for
every project.

Both branches are proved, not just the happy one:
`test_add_repo_refuses_a_path_that_is_not_a_repo_rather_than_storing_a_placeholder`
exercises the refusal, and `test_add_repo_refuses_a_bare_repository` the second
refusal; the two together are what make the happy path a measurement.

## T3.1 · the module is at 408 lines and the seventh verb will not fit

`tools_projects.py` is named in `test_the_three_modules_are_each_under_the_cap`
(`len(sizes) == 5` → `6`). It ships at **408** against the 450-line cap with six
verbs. `delete_project` plus its projection and its three-branch handler is
~60–80 lines, so the split the plan authorises —
`tools_projects.py` + `tools_projects_reads.py` — is very likely required when
the verb lands, and **both halves must be named on that line**, because a split
that escapes the enumeration is a split that hides growth.

## What T3.1 does **not** prove

- **Anything at all about `delete_project`.** Not the cascade, not P1's totality
  over the delete matrix, not P2's no-orphaned-session invariant, not E13's
  default refusal, not E9's reserved-project refusal. Six of the plan's seven
  verbs ship; the seventh has no test here because it has no code here.
- That any **route** reaches these tools (Phase 4) or that a person can drive
  them (Phase 9). The seam here is `invoke()`, and a route table that spells
  `workspace_id` would still 400 at runtime —
  `test_every_project_schema_spells_project_id_and_never_workspace_id` asserts
  this side of that contract only.
- That `add_repo`'s refusals are **complete** over the ways a path can fail to
  be a repo. Three are proved — does not exist, not a repo, bare. A path inside
  a repo the user cannot read, a submodule, and a path on a filesystem that
  disappears mid-probe are not.
- That the `local_destructive` classification is **gated** the way D58 intends
  at production's autonomy level. The tests install the shipped authorizer at
  `LEVEL_3`, which auto-approves; that a card is raised at a lower level is
  `tests/toolsurface/test_registry_gate.py`'s claim, not this file's.
- That `get_project`'s session list is **ordered**. It is whatever
  `reads.list_sessions` returns, and no assertion here pins it.
