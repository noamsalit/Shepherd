# T1.5 — the sweep

## T1.5 · the enumeration was short a **fifth** time, and the two new sites were again found by running · fixed in scope · owner: builder (Phase 1)

The plan measured 35 modules calling `upsert_workspace` (`grep -rl … | wc -l`
== 35). That number is exactly right, and 35 files were rewritten. It is still
not the sweep. Five categories were in the sweep and only two of them are
greppable by the plan's own discriminator:

1. **`store.upsert_workspace(name, root)` → `store.create_project(name=…,
   description=None)`** — 35 modules, mechanical, as planned.
2. **The eight N2 `list_workspaces()[0]` sites** — as planned. The eighth
   (`tests/orchestration/test_admission.py:321`, the `owned()` helper) survived
   the first pass because it is spelled across two lines from its use.
3. **Raw `INSERT INTO workspace (id, name, root_path, created_at)` in test
   fixtures** — `tests/store/test_session_verbs.py:43` and
   `tests/store/test_mailbox_verbs.py:43`. **Neither module calls
   `upsert_workspace`**, so neither is in the plan's 35 and neither is in its
   Files. They fail at *fixture setup* with `table workspace has no column named
   root_path`, i.e. as 39 collection-time errors rather than as assertion
   failures.
4. **`create_project` is no longer idempotent by name**, and three helpers
   depended on that. `seed()` in `tests/toolsurface/test_tools_m1.py` and
   `test_tools_m2.py` called `upsert_workspace("shepherd", …)` once per
   session and got one project; they now get one project per session, and
   `fleet_tree` returned three `workspaces` where the test expected one. This
   is **E1 landing on the fixtures**, and no grep for `upsert_workspace` or for
   `root_path` can see it — the call site is already rewritten and correct.
5. **Fixtures whose project had to be *admissible*.** §13's allowlist is repo
   paths alone after T1.9, so every fixture that spawned into a directory had to
   register it: `tests/orchestration/test_spawn.py`,
   `tests/orchestration/test_lifecycle.py`, `tests/toolsurface/test_tools_m3.py`,
   `tests/web/test_routes_m3.py`, `tests/qa/test_s2_spawn_stop_wake.py` (two
   sites). Five of those six modules are in no Phase 1 task's Files.

**Two more found only by the whole-suite run**, after every task's own Required
Checks were green:

* `tests/cli/test_commands.py:443,444,702` — `"schema version 3"`,
  `"expects 3"`, `"expects schema version 3"`. This is **F1's version-3 sweep
  on a fourth module**, and the plan's F1 table names three. `tests/cli` is in
  no Phase 1 task's Required Checks, so nothing before T10.2 would have caught
  it.
* `tests/qa/` — see (5).

**The generalisation.** T1.1's finding said *"running the checks is the
enumeration"*. T1.5 sharpens it: **running the checks named by the task is not
enough, because the sweep crosses task boundaries.** The two facts 004 changed
(the highest version moved; a fresh database is not empty) are joined by two
more the store rewrite changed (`create_project` is not idempotent by name;
the allowlist is repo paths), and all four are invisible to grep.

## T1.5 · the ordering in the plan is circular, and the circle was broken at the seam

T1.5's Required Checks include `tests/signals` and `tests/orchestration` green,
but `bind_cwd_to_repo` still called `store.upsert_workspace` until **T1.7** and
`_registered_roots` still read `workspace.root_path` until **T1.9**. T1.5 as
written cannot pass its own checks in its own position. It was executed as
T1.3 → T1.4 → T1.6 → T1.5(store) → T1.7 → T1.8 → T1.9 → T1.5(rest) → T1.10,
and every task's RED was taken at the **connection or module seam**, not through
a fixture that the sweep had not yet reached. Recorded rather than silently
reordered: the next revision should either fold T1.5 into T1.7/T1.9 or state
that its checks are the *union* of the tasks that follow it.

## T1.5 · the two greps in the Exit Criteria cannot be literally empty, and should not be

`grep -rn "upsert_workspace" src/ tests/` returns **nine** hits and all nine are
correct:

* `src/shepherd/signals/binding.py:228` and `src/shepherd/store/writes.py:113`
  — prose naming the verb each one *replaced*, which is the reason the new verb
  reads the way it does;
* `tests/boundaries/test_collected_node_ids.py:64-67` — the retirement entry,
  which must name the node id it retires;
* `tests/boundaries/collected_node_ids.txt:1180` — the frozen baseline, which is
  evidence and is never edited;
* `tests/store/test_verbs.py:828,914` and
  `tests/store/test_store_delegation.py:521` — the E1 measurement, the successor
  note, and `assert not hasattr(project_store, "upsert_workspace")`, which is
  the *positive* statement of the exit criterion.

No call site remains. The same applies to `! grep -rn "discover_repos"` in T1.8:
three hits, all inside that task's own retirement reasons. **A deletion's record
has to name what was deleted**, so an exit criterion written as a bare
`! grep` fails on its own bookkeeping. Read both as "no call site", and the
`hasattr` assertion is the machine-checkable half.
