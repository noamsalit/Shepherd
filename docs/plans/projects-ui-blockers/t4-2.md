All three were widened by hand and **re-derived from the table**, not copied
from the plan. Each one was observed red before `routes.py` changed.

| # | site | was | now | what it is |

## P13 — the shadow guard now covers `project_id`

`test_no_body_field_shadows_a_path_parameter` asserted that no POST route
declares `session_id` as a body field. It now asserts the same of `project_id`.

**Why it belongs here and not in Phase 9.** The route gate
(`test_the_route_table_declares_every_query_and_body_field`) checks `BODY_ARGS`
against the tool's schema and **never looks at path parameters**. A body field
spelled the same as a path parameter is therefore a mismatch that passes every
gate this repo has and disagrees with the URL only at run time — in a browser,
in Phase 9. Five of the seven new routes take `project_id` as a path parameter.

Both halves of P13 are present, and they are different claims:

- **the braces** — `..._no_body_field_shadows_a_path_parameter`: the field is
  declared **nowhere**, which is the property that actually holds today. This is
  the one the mutation found: reversing the merge order inside `resolve_post`
  *survived*, because `BODY_ARGS` had already dropped the colliding field.
- **the belt** — `test_the_path_parameter_wins_over_a_body_that_names_another
  _project` (new, in `tests/web/test_routes_projects.py`): declares `project_id`
  as a body field for the `delete` route under `monkeypatch` and watches the URL
  win anyway. This one *does* go red if the merge order is reversed. The route
  driven is `delete` deliberately: it is the one where reading the body instead
  of the URL destroys the wrong project.

## One measured correction

The first version of `..._is_never_read_as_a_project_detail` asserted that
`/api/projects/` is a **404**. It is not: `_segments` drops empty parts, so a
trailing slash yields two segments and resolves to `list_projects`. The
three-segment template cannot match it at all, so the safe answer is the list,
not a detail with an empty id. The test now asserts the measured behaviour and
says so, rather than being deleted or weakened.

A consequence worth recording: `_match`'s `if actual == "": return None` guard
is **unreachable** through `resolve`/`resolve_post` for that reason —
`_segments` has already dropped the empty part before `_match` sees it. Left
alone (this task is additions-only), noted here so the next reader does not take
it as the thing that holds the property.

## What T4.2 does **not** prove

- **That the page sends what the table declares.** Phase 9's.
- **That `BODY_ARGS`'s declared fields are complete** — that every field a tool's
  schema accepts is forwarded. The gate is one-way: declared fields must be
  schema properties, never the reverse. A body field the page needs and the
  table omits is silently dropped and shows up as a refusal.
- **That no *query* parameter shadows a path parameter.** `QUERY_ARGS` is
  unchanged by this phase and the widened guard covers `BODY_ARGS` only.
