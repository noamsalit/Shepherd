# T1.4 — the lifecycle writes

## T1.4 · E1 was shown red against today's code, and the measurement is here · owner: builder (Phase 1)

The plan requires E1 to fail before the fix lands. `upsert_workspace`'s body
was run verbatim against a 001→003 database (the schema it was written for),
because by T1.4 neither the column nor `rows.workspace()` can execute on the
new one:

```
E1 RED against today: same id? True | rows named api: 1 | /work/api root became: /personal/api
```

Two projects called `api` were **one row**, and the second registration
silently overwrote the first's path. That measurement is quoted in
`test_two_projects_may_share_a_name`'s docstring so the next reader does not
have to take the retirement on trust.

## T1.4 · a refusal is an exception for `rename`/`add_repo` and a **record** for `delete` · decided, not drifted

The plan's Produces fixes `delete_project -> DeleteOutcome` and
`rename_project -> Workspace | None`. Inside that, two spellings were chosen:

| verb | reserved project | absent project |
|---|---|---|
| `delete_project` | `DeleteOutcome(deleted=False, refused=…)` | `DeleteOutcome(deleted=False, refused=…)` |
| `rename_project` | `StoreError` | `None` |
| `add_repo` | `StoreError` | `StoreError` |

`delete_project` **never raises** because E13's dialog is rendered *from the
refusal* and an exception is not something a card can draw. `rename_project`
distinguishes forbidden from absent, because collapsing them would tell a
caller that deleting the row first would have worked.

## T1.4 · the `orphan` branch moves sessions **before** the cascade, and P2 is asserted after every cell of P1

`test_delete_is_total_over_its_matrix` builds `itertools.product((exists),
(has_running), OnRunning)` at test time — eight cells — and after each one runs
`SELECT COUNT(*) FROM session WHERE workspace_id NOT IN (SELECT id FROM
workspace)` and asserts 0. That is P2 riding on P1's enumeration rather than as
a separate test with its own, smaller, fixture. It reddens if the cascade is
reordered to delete `workspace` first, or if `orphan` moves the rows after the
`DELETE`.

Also asserted per cell: *never silent* — every outcome carries either `refused`
or `deleted=True`.

## T1.4 · `orphan` keeps only what is still running, and that is deliberate

`test_delete_with_orphan_moves_them_to_unassigned` asserts the **ended** session
went with the project. `orphan` is about what is still alive; a stopped row has
nothing left to keep visible, and keeping it would leave a growing tail of dead
rows in the reserved project that nobody deletes.

## What T1.4 does **not** prove

- That `kill` does anything. It is a `Callable[[str], None]` the caller injects,
  and the test injects `list.append`. That the real kill path stops a real pane
  is M3's property and is not re-proved here.
- That `add_repo`'s `root_path` is canonical or that `git_common_dir` was
  probed. `store/` performs no filesystem I/O at all (E10, the purity map);
  both arrive already resolved, and the verb that resolves them is Phase 3's.
- That `delete_project` is reachable from a tool, a route or a page. Phase 9.
