# T3.3 — the seventh verb: `delete_project`

Closes the blocker T3.1 recorded (`t3-1.md`). BASE `e4a0a75`, branch
`integration`.

## What was blocked, and what unblocked it

T3.1 shipped six of seven. `writes.delete_project` took a `kill` callable and
called it from inside the lambda `Store._write` runs on the single writer thread
after `BEGIN IMMEDIATE`, while the shipped kill path's first statement is itself
a store write — a permanent deadlock, reproduced then as *"DEADLOCK:
delete_project did not return within 10s"*.

**That verb no longer exists.** Phase 1's remediation withdrew
`writes.delete_project` and `Store.delete_project` and replaced them with two
halves:

- `Store.plan_project_delete(...) -> DeletePlan` — a pure read carrying
  `running`, `doomed` and the whole refusal;
- `Store.commit_project_delete(*, plan, killed=()) -> DeleteOutcome` — the
  commit, which **re-derives the decision inside its own transaction**.

So the tool kills **between** the two, on the calling thread, holding no lock.

## Where the kill comes from, and why

**Injected at registration, into the tool — never into a `store/` verb.**
`register_project_tools(*, store, kill: KillSession, now)`, where
`KillSession = Callable[[str], bool]`.

- **`bool`, not `None`.** `DeleteOutcome.killed` is *what the caller reports it
  actually killed*. The withdrawn callable could not report failure, and the
  shipped kill path answers `no_pane(session_id)` for any session it has no
  runner handle for — which is every *attached* one. A `None`-returning callable
  makes `killed` a list of sessions that may still be running.
- **Required at registration, defaulted in `build_project_tools`.** A caller
  that only wants to read the schemas gets `refuses_every_kill` (which answers
  `False`, so a commit refuses rather than deleting live rows); a composition
  that forgot gets a mypy error instead of a silent no-op.
- **`compose.py` injects the shipped `kill_session` path** (`tools_m3.kill`, the
  same implementation the button drives), so a session stopped by a project
  delete is recorded exactly the way any other kill is.

The alternative considered and rejected: have the handler re-enter `invoke()`
for `kill_session`. It reuses the chokepoint, but it nests an approval gate
inside a destructive verb already past its own gate, and a handler that can
block on a second approval deadline while holding a plan is worse than an
injection a test can program.

## The module split

`tools_projects.py` shipped at 408 against a 450 cap. The verb did not fit, as
T3.1 predicted. The plan's split was taken: `tools_projects_reads.py` holds the
two read verbs, the two projections and the shared schema vocabulary
(`PROJECT_ID`, `STRING`, `object_schema`, `MASTER_AND_HUMAN`, `Clock`). It is
the **lower** half — `tools_projects.py` imports from it and it imports nothing
back — so the cut cannot become a cycle.

**Both halves are named on the cap line**
(`test_the_three_modules_are_each_under_the_cap`, `len(sizes) == 6` → `7`).
Measured after: `tools_projects.py` **441**, `tools_projects_reads.py` **175**.
441 leaves nine lines of headroom; the next verb splits again.

**One thing the split broke, and the guard that caught it.**
`MASTER_AND_HUMAN` was at first defined once and imported by the other half.
`tests/boundaries/test_session_audience.py` reads every `ToolDef`'s `audiences=`
**statically**, resolving a bare name through the defining module's own
top-level bindings — it cannot follow an import, and it reports what it cannot
read as *unread* rather than letting it pass. Five tools went into `unreadable`
and the rule went red. The literal is now spelled in both halves, with a comment
in each saying why: a guard that can read both halves is worth one repeated
two-element frozenset. **That is the B1 branch of that rule doing its job** —
the half that keeps "every" true.

## The test that is the point

`test_the_kill_runs_outside_the_store_transaction`. Its injected killer
**writes to the store** — exactly what the shipped kill path does first — and
the call is made on a worker thread, asserted on a **10 s timeout**, because a
deadlocked call never returns to make an assertion. It is the same reproduction
the coordinator recorded against the withdrawn verb.

Both branches of every gate are driven:

| gate | branch driven | by |
|---|---|---|
| default `REFUSE` | refuses | `..._with_no_on_running_refuses_a_running_project` |
| default `REFUSE` | deletes | `..._deletes_a_project_with_no_running_sessions` (same call, nothing running) |
| `KILL` | kill lands | `..._kill_sessions_reports_what_the_kill_actually_did` |
| `KILL` | kill does not land | `..._keeps_the_project_when_a_kill_does_not_land` |
| `ORPHAN` | moves + severs | `..._orphan_moves_the_living_and_severs_the_lineage` |
| `on_running` value | outside the enum | `..._refuses_an_unknown_on_running_rather_than_guessing` |
| reserved project | refuses | `..._refuses_the_reserved_project_as_a_value` |

`test_delete_project_is_not_registered_and_the_reason_is_the_writer_thread` was
**deleted**, which is what it asked its reader to do, and replaced by
`test_delete_project_is_registered_and_reachable` — reachable through
`registered_tools()`, not merely present in `PROJECT_TOOL_NAMES`.

## What T3.3 does **not** prove

- **That the composed process's injected kill actually stops a pane.** The
  wiring is checked by mypy (the parameter is required) and the adapter is three
  lines over `tools_m3.kill`, but no test here drives `delete_project` through
  `compose()`: a `local_destructive` verb at the composition's autonomy level
  parks on the real approval deadline. The kill's two branches are proved
  against an injected killer, not against tmux.
- **That `killed` is complete over the ways a kill can half-land.** Two answers
  are driven — landed and did not. A kill that stops the pane but leaves the
  process, or that races the session ending on its own, is not.
- **Anything about the delete's ordering under concurrency** beyond the one
  thing `commit_project_delete` re-derives: a session arriving between plan and
  commit. Two deletes racing each other is untested.
- **That any route reaches this verb** (that is T4.1) **or that a person can
  drive the dialog** (Phase 9). The seam here is `invoke()`.
- **That `destroyed` is ordered** the way a page would want to show it. It is
  whatever the cascade's `ORDER BY started_at, id` returns; the tests assert it
  as a set where more than one row is involved.
