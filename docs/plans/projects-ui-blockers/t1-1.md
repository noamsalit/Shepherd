# T1.1 — migration 004

## T1.1 · the version-3 enumeration was wrong a *third* time · two more lines found by running the checks · blocks nothing (fixed in scope) · owner: builder (Phase 1)

**Symptom.** The plan's F1 table names sixteen lines across three modules and
states, as its own lesson, that "`== 3` is the wrong discriminator; the table
name is." Applying exactly those sixteen left T1.1's own Required Checks **red**
on two further sites that the table does not list:

1. `tests/store/test_migration_002.py::test_future_schema_refuses_to_start`
   (`:271-289`) builds its future sentinel by inserting `schema_migration`
   version **4** — the identical hazard the plan documents for
   `test_migration_003.py::test_future_schema_refuses_to_start_at_four`, on a
   second module. 004 makes 4 real, so the insert becomes a primary-key
   collision.
2. `tests/store/test_migrations.py::test_full_outer_join_is_available` (`:243`)
   asserted `rows == []` over `session FULL OUTER JOIN workspace`. This is
   **N1's shape on a third site** — the plan names two N1 sites
   (`test_fleet_page.py:104`, `test_binding.py:54`) and this is not one of
   them. The seeded `unassigned` row is an unmatched workspace, so the outer
   join now returns it.

**What was tried.** Both were found by *running* T1.1's Required Checks after
the sixteen named edits, not by grepping — a grep for `== 3` finds neither
(`:282` is `VALUES (4, …)`, `:243` is `== []`). Both were repaired as **body
rewrites**, so no node id moved and no extra retirement was needed:

- `test_future_schema_refuses_to_start` re-anchored at version **5**. Its name
  carries no version, which is exactly why it could be rewritten while its
  `at_four` sibling had to be retired.
- `test_full_outer_join_is_available` now asserts
  `rows == [(None, "unassigned")]`. This is a **stronger** witness of the
  capability than the old `[]`: an INNER JOIN over the same two tables also
  returns `[]`, so the old assertion could not distinguish the two join kinds.
  The new one can.

Also rewritten as stale prose, the same shape as the plan's own
`test_migration_003.py:227` note: `test_migrations.py:68`'s comment read
"M2's 002 and M3's 003 apply on top".

**What it blocks.** Nothing. Both fixes were inside T1.1's declared Files.

**The generalisation, because it is the reusable part.** Three careful
enumerations of this sweep have now been wrong (7, then 19, then 16). The
discriminator the plan reaches for — the table name — is right for the
`schema_migration` rows, and is still not sufficient, because the sweep is not
only about *counting migrations*. Two distinct facts changed with 004:
**the highest version is now 4**, and **a fresh database is no longer empty**.
Every site that encodes either fact is in the sweep, and neither is greppable.
Running the checks is the enumeration.

## T1.1 · exit criterion (d) had to be read out of the schema, not typed · no problem, recorded as a worked example · owner: builder

`test_the_unassigned_project_is_seeded_with_the_schema_default_owner` reads the
expected `owner_id` from `PRAGMA table_info(workspace)` and compares it to the
seeded row. Writing `assert row["owner_id"] == "local"` would have passed
identically against a migration that hard-coded `'local'` in the INSERT — i.e.
against exactly the mistake A10 exists to prevent. The check as written goes
red if the migration stops letting the default apply *and* if the default ever
moves.

## What T1.1 does **not** prove

- That any `src/` module can read the new shape. `store/models.py` still
  declares `Workspace.root_path` and `Repo.workspace_id` at this point; the
  tree is red by construction until T1.10.
- That the migration is reversible. It is not, and nothing here pretends
  otherwise: `DROP COLUMN` discards `repo.workspace_id` and
  `workspace.root_path` permanently. The backfill runs *before* the drop and is
  asserted row-by-row, which is the only guard available.
- That `DROP COLUMN` behaves this way on any host but this one.
  `test_the_host_sqlite_supports_drop_column` asserts `>= 3.35`, which is the
  version that introduced the statement — **not** a proof that 3.35 exactly
  reproduces 3.45.1's behaviour on the FK-referencing side. A2's probe was
  taken on 3.45.1 and the assertion is the narrowest honest guard, not a
  compatibility claim.
