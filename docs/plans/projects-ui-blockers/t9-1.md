## Five contract gaps. None is fixable from the page.

### 1. `DeletePlan.doomed` never reaches a consumer — the sentence D61 asks for cannot be written from the record

`reads.plan_project_delete` computes `doomed` — *"session rows this delete would
destroy, so the dialog can say what it is about to take **before** the button
rather than in the outcome"* — and `tools_projects.delete_project` **discards
it**: the refusal path returns `delete_outcome(plan.refusal)`, and
`delete_outcome` has no `doomed` key. `destroyed` is populated on success only.

So the refusal can say *"2 session(s) are still running"* and cannot say *"and
four hundred finished ones go with the project"*, which is the sentence the
code's own docstring says a person is owed.

**What the page does instead, and it is a copy:** it derives the count from the
detail it already holds — every session whose `ended_at` is set, which is
`running_sessions_for`'s `ended_at IS NULL` read the other way round. Two rules
now say the same thing in two languages, and the page's is the one that will
drift. **Asked for: `doomed` on the delete refusal.** No second call was made to
work around it, per instruction.

### 2. `DeletePlan.running` does not say which sessions are killable

The shipped kill answers `no_pane(session_id)` for any session with no runner
handle — every *attached* one — so `kill_sessions` on a project of discovered
sessions renders a button that cannot work, beside `orphan`, which can, as its
peer. The distinction is not in the record, so the page cannot warn in advance;
it says so in the choice's note (*"a session Shepherd does not own has no pane
to stop, so this can refuse again and say which"*) and shows what actually
happened afterwards. **Asked for: a killable/unkillable split on `running`.**

`test_a_partly_landed_kill_shows_what_it_stopped_on_the_refusal` is the honest
middle case: one of two sessions really is stopped, the commit half then refuses
over the other, and `killed` is non-empty **on a refusal**. The dialog shows it
there. A page that showed `killed` only on success would tell a person "nothing
happened" about an agent it had just stopped.

### 3. There is no verb that changes a description

`create_project` takes `description`; `rename_project` takes `name` only; no
other verb writes it. A project's description is therefore **write-once at
creation**. The Edit dialog renders the field disabled with the reason on it,
rather than accepting text it would silently drop. **Asked for:
`set_description`, or `rename_project(name, description)`.**

### 4. D60's *"a path may sit in more than one project, and the row says so"* is not reachable

`get_project` answers this project's repos; nothing answers *which projects hold
this repo*. Computing it needs a `list_repos` per project — an N+1 the
projections were explicitly shaped to avoid. The page therefore shows each path
in full and says nothing about sharing, rather than inventing it. **Asked for: a
`projects` (or `shared_with`) field on the repo projection.**

### 5. `delete_project` is destructive on its first call, so the page must confirm before it asks

With nothing running, the first POST *deletes*. There is no dry-run route and
`DeletePlan` is not exposed, so a page that "probed" for the refusal in order to
render a confirmation would destroy any project that happened to be idle. The
dialog therefore states the consequences from the detail it holds, and the first
POST happens only after a click on a named, danger-marked choice. This is a
consequence of gap 1 and would close with it.

## The shell contract — what the integration pass must honour

This phase owns `src/shepherd/web/static/projects.js` alone. It edits no shell
file. What it needs from `index.html` / `app.js`:

1. **`<div class="panes2" id="page-projects" data-level="list" hidden>`**, empty.
   `mountProjects()` calls `replaceChildren()` on it and builds both panes and
   both dialogs inside it. The page reads and writes `dataset.level`
   (`"list"` / `"detail"`) — that is the phone's back behaviour and `app.css`'s
   `.panes2[data-level=…]` rules already implement it.
2. **A nav entry `.nav-item[data-page="projects"]`** that reveals the root, the
   existing shell vocabulary; `tools/render_check.py::NAV_SELECTOR` is the same
   string.
3. **`import { mountProjects } from "./projects.js";`** and one call to
   `mountProjects()` on boot (or on first reveal). It returns `{ reload }`; call
   `reload()` from the SSE envelope handler if project rows should follow
   events. Nothing here is on a timer (§12: no polling).
4. **`#dlg-project` and `#dlg-delete` must NOT be declared in `index.html`.**
   This is a deliberate departure from T9.1's *Consumes* line. This module is
   the only reader of those dialogs, and a shell that ships empty slots for a
   page it does not otherwise know is one contract in two files. They are built
   by `mountProjects()` with exactly those ids, inside `#page-projects`.
5. **Session links:** each session renders as
   `<a class="mini-open" data-page="flock" data-session-id="…"
   href="#flock/session/…">`. The shell must handle a click on a `[data-page]`
   anchor the way it handles a `.nav-item`: show the Flock and select
   `data-session-id`. The `href` is a real target so the row is a link (focus,
   middle-click) and not a div that listens; the page performs no navigation of
   its own.
6. **Two gates go red until the wiring lands, and both are the integration
   pass's to close.** They are red on this branch, deliberately, and are named
   in the report:
   * `tests/web/test_session_wiring.py::test_every_shipped_module_is_reachable_from_the_page`
     — `projects.js` is not imported from `index.html` yet.
   * `tests/boundaries/test_consumer_surface_frozen.py::test_completing_l4_changed_no_consumer_byte`
     — Gate A, which was **already red on this base** for `web/static/app.css`
     (T5.2) and now also names `web/static/projects.js`. The manifest is
     re-based once, by the integration pass, and this task is not permitted to.

## Smaller notes

* **`on_running` is hardcoded as `kill_sessions`, never `kill`.** The plan
  carries the stale `["refuse", "kill", "orphan"]` at two places; `OnRunning` in
  `store/models.py` is the source of truth, and `"kill"` is what the tool's own
  negative test feeds it. No route exposes a tool schema, so a page cannot learn
  the values at run time — which is exactly why the constant is spelled beside a
  comment naming the enum.
* **The first delete POST carries no `on_running` key at all** — not
  `"refuse"`. A field that is never in the body cannot be edited out of it, and
  default-refuse has to be unskippable by omission.
* **F6's one `innerHTML`:** `BACK_BUTTON_P()` (prototype line 3101) is rewritten
  with `createElementNS`. `projects.js` is appended to
  `EXPECTED_MODULES` in `tests/web/test_frontend_escaping.py` — a closed set by
  design, so a scan that never enumerated the file would have reported it clean.
  That one-line edit to a shared test module is the only file outside
  `projects.js` and the new test that this task touched.
* **`Unassigned` offers no lifecycle control at all** — absent, not disabled —
  and the assertion is over the whole detail pane (`button` count is 1, the Back
  button) rather than over three named ids, so a fourth control added later
  trips the same line. E7/E8/E9 are additionally driven through HTTP here, so
  the design (no control) and the guard (the store refuses anyway) are both on
  the record.
* **The work-source block is `not built`** (D63/D64/W3): a label and a sentence,
  and the test asserts the section contains **zero** `select`, `input` or
  `button` elements.

## What this does not prove

No pixel (Phase 10's `render_check.py`), no phone browser, no tunnel. Not that
the Flock opens when a session link is clicked — the anchor's shape is asserted,
the routing is the shell's. Not that `index.html` mounts the page. Not the
ticketing-system configuration, which is not built. And not the sentence in gap
1, which no consumer can currently write.
