## The trap, and the one entry

**`app.css`, `app.js` and `index.html` got a digest update and NO
`post_milestone` entry.** They are already in `rebase.regenerated_paths`, and
`test_a_rebase_declares_every_path_whose_digest_moved` asserts
`later.isdisjoint(declared)`. Adding an entry for any of them fails that
assertion — a path may never be relaundered through the second list. A builder
hit exactly this today and the gate refused it.

**`web/static/escape.js` got no entry either.** It is byte-unchanged (ADR-P6),
so it is not in `moved_paths` at all, and declaring it would be a false record
of the other kind — the equality would then demand a movement that never
happened.

**`web/static/rail.js`'s entry was REWRITTEN, not appended to.**
`post_milestone_paths` asserts `len(seen) == len(set(seen))`: entries are per
**path**, not per edit, so a path carries exactly one entry and that entry has
to describe the path's *whole* divergence from the step-0b baseline. The
existing sentence — *"Comment text only: no statement, no selector and no
behaviour changed"* — was true of the 2026-09-20 publish scrub and became false
the moment the file was deleted. Leaving it would have been a false record in
the one gate whose entire purpose is an honest one. The new `why` carries both
halves: the scrub that first moved the path, and the deletion that ended it,
with D66 named and the surviving projection pointed at.
