### The browser, because this page's risk is what a person can read

`tests/web/test_settings_live.py` — seven tests, chromium against the **real**
loopback server: real route table, real `invoke()`, real `Store`, real
`ApprovalStore`, modules fetched from `/static/`. The only bytes the test

It drives the mount in **the shell's order** — mount while the root is still

proves nothing about the page's own whitelist. The argument is asserted
**present on the wire** and **absent from the pixels** — one without the other
is either a vacuous exclusion or an unexplained gap.

### Two findings the browser produced that reading could not

* **`.col-head` carries `text-transform: uppercase`, and Playwright's
  `inner_text()` returns the transformed text.** The first Settings markup put
  the page name in a `.col-head`; `render_check.py` read `SETTINGS` and reported
  *"settings is missing 'Settings'"* at both viewports. The title is a
  `.proj-band > .proj-title` for that reason, and a test now pins the lesson by
  asserting both that the rule has the transform and that the name is not in an
  element that carries it. **This affects every page whose only rendering of its
  own name is a `.col-head`** — worth a look on Flock and Queues.
* **The same transform on `.src-state`.** Discovery's hook status is therefore
  asserted with `text_content()` (the datum the module put in the DOM) and
  separately with `inner_text()` (how the stylesheet paints it). Asserting the
  painted string as if it were the datum would have been a test that passes for
  the wrong reason.

**M1 is the one worth reading twice.** It was caught by the static table test
and **missed by the live test**, which at that point never opened the panels.
That is a control exercising one branch of two: the table is where the reason is
*written* and the panel is where it is *read*, and a gate on only one of those
is a gate on half the promise. `6a345aa` adds the pixel half. The ledger records
the miss rather than only the repair, because the repair is the cheap part.

**M5 also produced a finding that was wrong, and it is kept here because the
way it was wrong is the reusable part.** The M5 run appeared to show
`render_check.py` printing two failures and then exiting 0 — a gate whose exit
code does not follow its own report. It was written up as a defect in the tool.
It is not one. The command had been piped through `head`, so the `$?` that was
read was **`head`'s** exit code and never the checker's. Re-run unpiped, with
the output redirected to a file:

```
$ .venv/bin/python tools/render_check.py --file <harness with the plant> > rc.txt 2>&1
TRUE EXIT=1
FAIL [phone] on arrival: 2 page roots visible at once
FAIL [desktop] on arrival: 2 page roots visible at once
```

The checker is correct. The measurement was not. *When a result surprises you,
suspect the observation method before the system* — and a pipeline's `$?` is
the last command's, which is a thing that is known and was still got wrong under
a shell one-liner. Every exit code quoted in the table above was taken from an
unpiped run or from `PIPESTATUS[0]`; this row is the one that was not, and it
produced a false finding about someone else's tool.

The pytest gate caught M5 independently, so the property itself was never in
doubt.
