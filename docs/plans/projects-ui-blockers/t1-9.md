# T1.9 — the allowlist becomes the repo paths alone

## T1.9 · all four surviving properties were kept, and the easy-to-lose one has a two-branch control · owner: builder (Phase 1)

| property | where | how it is proved |
|---|---|---|
| components, never strings | `_canonical_cwd`'s `root in candidate.parents` | the five parametrised escapes, `repo_name_is_a_string_prefix` in particular |
| innermost wins (D22) | `max(matched, key=…len(root.parts))` | `test_the_innermost_registered_root_wins` |
| empty means refuse | `if not roots:` | `test_a_project_with_no_repo_refuses_everything` |
| **never silently narrows** | the refusal at the canonicalize site | `test_every_registered_path_is_either_admitted_or_named_in_the_refusal` (P5) |

P5's test runs **both branches in one body**, and says so: with only the good
repo the cwd under it is admitted; with the bad row added, the same cwd is
refused **and the bad path is in the message**. One branch alone would leave
either "refuses" or "names it" unproved, and replacing the refusal with a
`continue` has to redden both halves, not one.

## T1.9 · one behaviour was **added**, deliberately: a missing project is its own refusal

The plan says "use `Store.get_workspace` for existence". Before, an unknown
`workspace_id` produced an empty allowlist and therefore the *"has no
registered repo"* message. It now produces *"there is no project X"*. A missing
project and an empty one are different facts and an operator fixes them
differently; reporting the second for the first is the same shape of lie the
silent-drop rule exists to prevent.

## T1.9 · four retirements, eleven body rewrites — and the arithmetic is checkable

The file carries exactly **15** frozen node ids. The four retired are the four
whose *names* carry the workspace-root premise:

* `test_a_repo_registered_outside_its_workspace_root_is_admitted` — after 004
  every repo is "outside" the root, because there is no root. Successor:
  `test_a_registered_repo_admits_a_spawn`.
* `test_a_workspace_with_no_root_path_still_admits_its_registered_repos` — the
  condition in the name is now universal. Successor:
  `test_add_repo_widens_the_allowlist`, which measures the allowlist *across*
  the registration instead of asserting it once afterwards.
* `test_the_workspace_root_stays_a_permitted_root_beside_the_repos` — asserts
  the opposite of what D57 decides. Retired rather than inverted: a test whose
  name promises the root stays and whose body proves it is gone is a trap.
* `test_a_workspace_with_neither_a_root_nor_a_repo_refuses_everything` — half
  the setup in the name cannot be built. Successor:
  `test_a_project_with_no_repo_refuses_everything`.

4 + 11 = 15. Every other id kept its name and had its body rewritten, including
E12's `test_a_registered_root_that_will_not_canonicalize_refuses_and_names
_itself` and the five escapes.

## What T1.9 does **not** prove

- That `add_repo` is reachable from the UI, which is what would actually widen
  an allowlist in practice. Phase 3 and Phase 9.
- That `repo.active` narrows anything. Nothing in `store/` writes `0`, and
  `test_nothing_deactivates_a_repo_so_list_repos_needs_no_active_filter` is
  still the tripwire that says so.
- That an allowlist of *many* repos performs. The match is a linear scan over
  `list_repos`, unchanged in shape from before.
