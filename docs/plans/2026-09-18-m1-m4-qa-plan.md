# QA plan — M1 through M4, the composed system

**What this pass is for.** 1791 tests pass and 57 live tests pass. They were written by the people who
built each milestone, so they are strong on each milestone's own seams and **structurally weak exactly
where milestones meet** — each was written before the next existed. This pass tests the *product*, not
the modules.

Three researchers read three disjoint sources (the spec's promises, the shipped entry points, the
suite's negative space). Where they disagree, that disagreement is itself a scenario.

## The headline gap, verified by the router

**No shipped tool has ever crossed a gate that could say no.** `tests/chokepoint_fixture.py`'s
`install_test_chokepoint` defaults to `AutonomyLevel.LEVEL_3`, which §11's table auto-approves for
every class and every audience. Six suites import it. A grep for `LEVEL_2` across the three
shipped-tool suites returns **nothing**. Every card, block, approve, reject, timeout and withdrawal in
the deterministic suite is proved against **synthetic** tools (`tool_for(BlastClass.X)`,
`_destructive_tool()`). The one time a real destructive tool met a blocking gate was a single live turn
— and that call was **inert by construction** (the row had no handle, so the kill returned `no_pane`
without building a tmux argv).

This is the repo's signature defect at the integration level: the gate is proved, the tools are proved,
the *composition* is not.

## Scenarios

Each names what it drives, what must be observed, and **what a lying implementation looks like** — the
question this repo asks of every check.

### S1 — the gate that can say no *(highest value, cheapest)*
Drive **every registered `ToolDef`** × **both `AutonomyLevel` members** × **each audience in its own
`audiences` set**, through the shipped `invoke()` with the shipped chokepoint. `AutonomyLevel` has
exactly two members, so this is **full-combinatorial and small**, not a sampling problem.

Observe per cell: whether a card was raised; whether the **handler ran** (a counting handler, asserted
zero on deny); the audit record's `decision` / `approved_by` / `result`; and that a denied call returns
a typed failure rather than a silent success.

*Lying implementation:* one that raises cards correctly but runs the handler anyway; one that allows at
`LEVEL_2` because the test only ever asked at `LEVEL_3`. **Enumerate the population at test time** —
a literal list of tools is how this goes stale.

### S2 — master spawns, session stops, wake carries it into the next turn
The full chain nothing exercises: a master turn spawns a session → the session stops → M2 classifies it
→ `wake.drain` picks it up → the **next** turn opens with it in the summary.

Observe: the stop verdict on the row M4 created; the wake set containing exactly it; the stamp moving
**once**; a second drain yielding nothing.

*Lying implementation:* a wake set built from a fixture rather than from the session the master actually
spawned. **The session id must be the one the spawn returned.**

### S3 — M3's terminal under M4's gate
`get_session_output` / `terminal_snapshot` driven **through a gate that can block**, at both levels, as
each audience that declares them. These are read-class, so §11 lets them through without a card — which
means the only thing to assert is **the audit record**, and G-M4-17 records that a read in a
non-composing process is unaudited.

*Lying implementation:* one that audits reads only when a chokepoint happens to be installed by a test.

### S4 — the Needs-You rail, fed by three milestones at once
The spec puts the rail on **every** page and forbids generic text: each row must name the actual ask.
Its rows come from M2's signals, M3's owned sessions and M4's approvals **simultaneously**.

Drive all three sources into one projection and assert the rows carry their own asks, the count is
right, and the empty state is distinguishable from the absent state. **Deterministic only** — this host
has no browser, so assert the projection, never the render.

### S5 — projection bounds
At 1 / 5 / 25 / 200 sessions (T23's `seed_fleet` builds these), record `fleet_summary` and `fleet_tree`
sizes. **G-M4-8 is a design decision and not this pass's to close** — but nothing currently asserts any
bound at any size, and the measurement is the input to the decision.

### S6 — restart continuity, asserted as the gap it is
`master_session_id` is persisted; `MasterRuntime.resume()` **has no caller in `src/`**. Assert the
writer works and **record the missing reader honestly** rather than testing around it. A scenario that
passes here would be lying about a half-built capability.

### S7 — shutdown with work in flight on a thread shutdown does not own
§T25-8's production shape: the HTTP server serves off threads not in `Controld.threads`, so a worker
released by shutdown's withdrawal can meet a closed store. Drive it. Clause 20's promise — nobody left
**blocked** — must hold; record whether the released caller gets D54's refusal **or** a raise, and do
not launder the second into the first.

### S8 — `shepherd status` against a running daemon
M1 T18-1, recorded open: the registry is a process global, so a `shepherd` the daemon did not start has
no fleet tools. Observe what a user actually sees.

### S9 — the install path *(and the macOS handoff depends on it)*
**Nothing is installed on this host** — the three console scripts exist only as declarations. Drive
`pip install -e .` into a throwaway venv, then run each console command. This is the first thing a Mac
will do, and it has never been exercised.

## Rules this harness obeys
Read `CLAUDE.md` first. Never `tmux kill-server` without `-L`; never name the socket `shepherd`; session
names are read, never hard-coded. Never write under `~/.claude/` — its sha256 is checked on both sides
of every live test. Every live run gets explicit `--settings` into `tmp_path`, a scrubbed env, a
non-repo cwd, bounded subprocesses, and leaves no process behind.

**QA never edits product code.** A defect found here is reported, with its evidence, and is worth more
than a fix.
