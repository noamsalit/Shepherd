## Siblings left open (recorded, not changed)

- **A refused start consumes an attempt.** The link is written right after `create_owned_session`,
  as the plan orders it. So a declared retry whose `runner.start` then refuses leaves a linked row
  ended `refused` (D73). That row is excluded from the wake set, but it is in the lineage: RD-2 names
  it as X's retry, and a retry of it is capped. This is consistent with C-M3-7 (the attempt stays
  visible) and with "the cap counts attempts". If the owner wants refused starts not to count, the
  link would move after `runner.start`. That is a D70 refinement, not a P5 change.
- **Sibling race.** Two concurrent spawns declaring the same `retry_of` could both pass RD-2's read
  before either links. `link_retry` refuses a relink of one row, but not two rows naming one target.
  The master's calls run sequentially inside one turn, and a human double-click is the only
  concurrent source. Out of scope, like P4's T12 reconcile of partial rows.
- **`link_retry` raising.** In principle `link_retry` can raise `StoreError`, which would break
  "every failure is a `SpawnRefused`". It raises only for an unknown target or a relink, and step 1
  and the fresh row rule out both. There are no session deletes in the tree, so it is not guarded.
- **`tests/qa6/catalog.py:122`** still describes M14 as "(C-3)", with expected "FAIL (no production
  path sets `retry_of`)". That is the comparison set's metadata, which P15 reconciles. It was not
  edited here.

## REM-FIX 1 (code-reviewer + failure-hunter, scope ALL_ISSUES)

Router decisions, final (owner granted full autonomy). Each is a **D70 refinement**:

- **D70-R1: only a started attempt joins the lineage.** The link moves from right after
  `create_owned_session` to right after `store.set_runner_handle`. A retry whose `runner.start`
  refuses (e.g. a transient tmux timeout, `runner/local.py:285`) ends its row `refused` (D73) with
  `retry_of` NULL, so it consumes nothing: the next retry of X is still X's first, and neither RD-2
  nor the cap refuses it. This **supersedes** the sibling "A refused start consumes an attempt" above.
- **D70-R2: a link the store refuses is a `SpawnRefused`.** `StoreError` from `link_retry` is
  caught; the row is ended `refused` through `Store.end_refused` (a failed ending is swallowed, the
  same shape as the runner-refusal path), and the answer is one sentence:
  `"'<new>' could not be recorded as a retry of '<X>': <store's reason>"`, cap `None`. This
  **supersedes** the sibling "`link_retry` raising" above (that ledger claim was not a guard).
- **D70-R3: RD-2 at a full master lineage is the cap.** When the caller's origin is the master's
  (`MASTER_ORIGIN`) and `retry_chain_depth(existing) >= MAX_MASTER_ATTEMPTS`, the refusal is
  `"'<X>' was already retried as '<r1>', and that lineage has used its 2 master-initiated attempts
  (D31): read their conclusions, and ask the human to re-run it."`, carries
  **`cap: "retry_cap_reached"`**, and bumps `wake_retry_cap_reached` once, like the cap refusal.
  Builder's choice within the ruling: the `cap` value. The ruling fixed the anomaly; carrying the
  same `cap` label keeps the refusal and its count saying one thing to the master and the fleet.
  Human callers keep `"… ; retry that one instead"`, cap `None`, no count.
- **D70-R4: a retry names a stopped attempt in the same project.** Before admission, with no row and
  no anomaly: a target that is not `stopped` → `"'<X>' is <state>, not stopped: only an attempt
  that has ended can be retried"`; a target whose `workspace_id` differs → `"'<X>' ran in another
  project ('<ws>'): a retry starts in the project its attempt ran in"`. Order: unknown, not
  stopped, other project, RD-2.
