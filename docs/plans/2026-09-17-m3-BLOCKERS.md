# M3 blockers — append only

Per the plan's blocker protocol (§0, K7), in M1's and M2's format:

`T<id> · symptom · what was tried · what it blocks · owner: evidence gap | decision gap | host gap | upstream bug`

An **evidence gap** names the probe that closes it — never guess a shape.
A **decision gap** is written *decision · pressure · options · recommendation*,
with the recommendation **not applied**.

## T7-1 · Task 7 names the wrong rule as the one that catches a planted `runner/` branch · owner: plan correction, resolved in place

**Symptom.** Task 7's prose says the **layer** rule (`test_layer_direction`) is what
fails the build if `runner/` answers a host question itself. It does not, and
cannot: `shepherd.runner` and `shepherd.host` are **both L2**
(`tests/boundaries/_imports.py`), so `runner` importing `host` is a legal
sideways import and the layer rule is silent on it.

**What was tried — and this is the useful half.** T7's builder planted a real
violation in `src/shepherd/runner/local.py`:

```python
if supervision.kind == "systemd_user":
    return ["systemd-run", ...]
```

The rule that actually bit was **`test_kind_is_never_branched_on`**:
`shepherd.runner: .kind compared against a string literal`. A second plant using
`sys.platform` was caught by **`test_no_platform_branching_outside_host`**:
`shepherd.runner: platform identifier 'sys.platform'`. So the *protection is
real and the plan's conclusion holds* — `runner/` genuinely cannot answer a host
question — but it is enforced by two different rules than the one named.

**What it blocks.** Nothing. It is recorded because a builder who reads the plan,
plants a violation, and watches the *named* rule stay green would reasonably
conclude the protection is absent and add something. The correction costs one
sentence in Task 7 and is worth more than the sentence: **a plan that names the
wrong enforcing rule teaches a builder to distrust the rule that is working.**

**Note on the sanctioned form.** `test_kind_is_never_branched_on` forbids
`.kind == "<literal>"` **everywhere, `host/` included**. The accepted shape is
comparison against a named constant the defining layer exports — T7 added
`SUPERVISION_KIND_SYSTEMD_USER` to `host/base.py` beside `SupervisionKind` and
compared against that. **No exemption was added**, and the rule's own negative
fixture already demonstrates this form.

## T7-2 · a builder removed a shared package directory to revert its own plant · owner: process, closed by the router

**Symptom.** T7 proved its boundary claim by planting
`src/shepherd/runner/local.py`, then reverted with `rm -rf src/shepherd/runner`
— while **T5 was concurrently creating that exact package**. T7 flagged it
itself rather than burying it, which is the only reason it is legible.

**What was checked.** No damage: T7's deletion was at 08:20:11 and T5's
`runner/__init__.py`, `tmux_cmd.py`, `base.py` and `tests/runner/*` are all
08:22:48–08:27:15, verified by mtime. T5's work was never in the blast radius.

**What it blocks.** Nothing, this time — and "this time" is the entire point.
Plant-and-revert is now how this repo proves a check bites (it is required by
five M3 properties and was used by every builder this session), so the idiom
will recur under concurrency.

**The rule, for every future brief.** A plant is reverted by **restoring the
exact file** — from a scratchpad backup, or by deleting only the single file the
builder itself created — never by removing a directory the builder does not
own. A recursive delete in a shared tree is a blast radius, and this project has
one incident already from a command whose blast radius was wider than its
author's intent (§18, 2026-09-12).

## T5-1 · K6's "`kill-server` is forbidden in `src/` outright" and K16's runtime predicate cannot both be literal · owner: decision gap

**Symptom.** K6 says the verb "is forbidden in `src/` outright — production tears
down one session at a time", and Task 5's required check is named
`test_kill_server_appears_nowhere_in_src`. K16 says `check_tmux_argv` must refuse
"a `kill-server` argv whose socket" is not a throwaway — and `check_tmux_argv`
lives in `src/shepherd/runner/tmux_cmd.py`. A predicate that refuses the verb has
to be able to recognise it, so under a literal reading of K6 the one function K16
mandates cannot be written in the package K16 puts it in.

**What was tried.** Three spellings that avoid the literal, each rejected:
(i) matching a prefix/suffix pair (`startswith("kill-")` and `endswith("server")`)
— a spelling of a spelling, and it also matches `kill-serverless`;
(ii) importing the word from `tests/` — production importing its own rule's test
vocabulary, and `tests/` is not on the product's import path;
(iii) assembling it from halves inside `tmux_cmd.py` (`"kill" + "-server"`) — this
works, and is the idiom the shipped `tests/e2e/test_live_attached_session.py`
used, but it hides the predicate's most important word from every reader and from
`grep`, in the one file where a reader most needs to find it.

**What it blocks.** Nothing — T5 is built and green. What is at stake is which
sentence the next builder reads as the rule.

**Decision.** What exactly is forbidden in `src/`: the *word* `kill-server`, or
the *construction* of an argv containing it?

**Pressure.** K6's wording is the strict one and the strictness is deliberate
(§18). But K6-a's own reasoning is that strictness with nowhere to go
manufactures pressure toward the unsafe form; a rule that forbids the predicate
from naming what it refuses is that shape again, one level up. Against that: any
narrowing of a rule written because of an incident deserves to be a decision
someone made, not a decision a builder made at 3am.

**Options.**
1. **Position-based rule (what is built, pending this entry's resolution).** The
   verb may never appear in `src/` as a **command word** — an element of a
   sequence display, or the value bound to a name. A constant in a comparison
   (`if "kill-server" in argv`) is a *check*, builds nothing, and is permitted.
   The test is renamed `test_kill_server_is_never_a_command_word_in_src` so its
   name states the actual rule, and it asserts **both** halves against
   `tmux_cmd.py`: the file does mention the verb (so the predicate really checks
   for it) and does not build it. This is the same value-following distinction
   the one-builder rule already makes for `registry.py`'s `fields.get("tmux")`.
2. **Literal ban plus assembly** — keep `test_kill_server_appears_nowhere_in_src`
   exactly as named and spell the verb as `"kill" + "-server"` inside the
   predicate. Costs: the repo's most safety-critical word becomes ungreppable in
   the file that enforces it, and the rule's own name becomes a thing that is
   true only because the code hid from it.
3. **Move the predicate out of `src/`** — rejected on sight: the exec site is in
   `src/` (T8), and a guard that does not run at the exec site is ADR-M3-8's
   rejected alternative.

**Recommendation (NOT applied as a decision — see below).** Option 1. The
property K6 is protecting is "production never *issues* a server-wide teardown",
and a comparison issues nothing; `tests/boundaries/_taint.py:5-9`'s finding is
that a rule about a value has to follow the value, and the value here is the
argv, not the token. **What is built is option 1**, because K16 requires a
working predicate in `src/` and no option leaves T5 both green and literal — so
this entry records the narrowing rather than deferring it, and asks for it to be
ratified or reversed. Reversing it is one edit (`tmux_cmd.py`'s single
comparison, plus the rule's `command_word_sites` call becoming
`mentions_literally`) and the test suite says so.

## T5-2 · `tests/boundaries/fixtures/` has to be outside the tree-wide tmux scan · owner: plan correction, resolved in place

**Symptom.** Revision 2 widened the tmux rules' scope to `tests/**/*.py`
recursively. The seven planted fixtures Task 5 also mandates live at
`tests/boundaries/fixtures/` and each one **is** a violation by construction, so
the widened scan reports the suite's own evidence as a finding.

**What was tried.** Nothing else works: the fixtures cannot live outside `tests/`
(nothing else is collected), and they cannot be written as non-violations
(their whole job is to make the rule bite).

**What it blocks.** Nothing. Recorded because it is a **stated scope, not an
exemption**, and the difference has to be checkable: the fixtures directory is
excluded, and `test_the_scan_scope_is_what_it_claims` asserts that the excluded
set is exactly that directory, is disjoint from the walked set, and that every
`runner_*` file in it is named by a self-check in the scanning module — so the
exclusion cannot grow without a test naming what grew it.

**RATIFIED 2026-09-17 by the router — option 1 stands.** The builder was right to
build it and right to refuse to call it settled.

The property K6 exists to protect is *"production never **issues** a server-wide
teardown"*. A comparison issues nothing. Option 2 would satisfy K6's letter by
spelling the verb `"kill" + "-server"` inside the predicate — which is precisely
the concatenation idiom these rules forbid everywhere else in the tree, adopted
in the one file whose entire job is to refuse it. A rule that forces its own
enforcer to hide from it has stopped being about the property and become about
the grep.

The decisive point is that option 1's test is **stronger**, not weaker, than the
literal ban it replaces. `test_kill_server_is_never_a_command_word_in_src`
asserts *both* halves against `tmux_cmd.py`: the file **does** mention the verb,
so the predicate demonstrably checks for it, and **does not** build it. A literal
ban cannot express the first half at all — under option 2 a predicate that had
silently stopped checking for `kill-server` would pass, because absence is
exactly what that rule rewards. Option 1 fails in that case.

This also keeps the repo's most safety-critical word greppable in the file that
enforces it, which is what a human auditing §18's rule after an incident will
actually do.

Verified by the router before ratifying, by calling the predicate directly: the
user's socket is refused via `kill-server`, via `kill-session -t =main:`, via a
plain `list-sessions`, and **even when `permitted=frozenset({"shepherd"})` is
smuggled past `permitted_sockets`** — because `FORBIDDEN_SOCKET` is tested before
the allow-list is consulted. `tmux kill-server` with no `-L` is refused, and so is
`["tmux","-V",";","kill-server"]`, because `-V` is matched by tuple equality
rather than by prefix. `kill-server` is permitted only on `^shepherd-m3-`.

K6's wording in the plan should be read as option 1 states it from here. No
reversal.

## T4-1 · Task 4's two rebind checks contradict each other, and one verb cannot satisfy both · owner: decision gap

**Symptom.** Task 4 names two required checks on the same verb:

* `test_an_unbound_ask_fork_row_is_bindable_exactly_once` — "**goes red** if
  `rebind_engine_session_id` can overwrite an already-bound id, which would
  silently repoint a live row";
* `test_rebind_moves_the_engine_session_id_and_keeps_the_row` (C14) — `/resume`
  ends the old `session_id` **in the same pane**, so the row keeps its identity
  and **changes** `engine_session_id`.

The first forbids exactly what the second requires. Both callers are real and
both are in this plan: T15's P2-refused branch binds an unbound `ask_fork` row
from the `-p` result object (A25), and T12's `rebind` moves a **bound** id on a
live row (C14). `Produces` gives one verb with one signature for both.

**What was tried — and this is the useful half.** The verb was first built as a
compare-and-set: read the current binding, `UPDATE … WHERE id = ? AND
engine_session_id IS <what was read>`. Under six concurrent binders each running
`BEGIN IMMEDIATE`, that settles **nothing**: the transactions serialise, so every
caller reads the value the previous one committed and every CAS matches. The run
is recorded verbatim — `exactly one bind may win, not ['fork-1', 'fork-0',
'fork-3', 'fork-4', 'fork-5', 'fork-2']`. A CAS only refuses a binder whose read
was invalidated **in flight**, which under D37's one writer cannot happen at all.
So the "exactly once" property is not merely untested by the shipped verb; with
one verb carrying C14's semantics it is **unreachable**, and a test asserting it
would have to assert something weaker while keeping the stronger name.

**What it blocks.** Nothing at T4 — the verb ships with C14's semantics, which is
what T12 needs and what the second required check asserts. It blocks T15 having
the protection its own check names: a second `ask_fork` bind silently repoints
the row.

**Decision.** Is `rebind_engine_session_id` one verb (a move) or two (a
first-time **bind**, and a **move** of an existing binding)?

**Pressure.** D33's verb surface is the reason `store/` can be ported: a verb
names an intent, and *bind an unbound row* and *move a live row's binding* are
two intents that differ in exactly the way the caller cares about. Against that:
`Produces` and T15's `Consumes` both name one verb, adding a second changes a
later task's stated surface, and the plan's hard rule is that a builder does not
quietly widen another task's inputs.

**Options.**
1. **Split the verb.** `bind_engine_session_id(connection, session_id, id)` —
   `UPDATE … WHERE engine_session_id IS NULL`, refusing when the row is already
   bound (T15's caller, and the "exactly once" check becomes literally true);
   `rebind_engine_session_id(connection, session_id, id)` — the C14 move,
   refusing when the row is unbound (T12's caller). Each refusal names the state
   it found. Costs: one verb more than `Produces`, and T15's `Consumes` line
   changes.
2. **One verb, C14 semantics (what is built).** A bind and a move are the same
   statement. The "exactly once" property is not held; T15 must not call it
   twice. Costs: the failure it was meant to prevent — a live row silently
   repointed — is possible and nothing in the tree refuses it.
3. **One verb, bind-once semantics.** Refuse any write to an already-bound row.
   Rejected on sight: it makes C14 unimplementable, and C14 is a captured fact
   about `/resume`, not a preference.

**Recommendation (NOT applied).** Option 1. **What is built is option 2**, because
option 2 is what the C14 required check asserts and what T12 consumes, and
because choosing option 1 would change a later task's stated inputs — which is
this plan's own hard rule about builders. The gap is left **visible in the
suite** rather than in this file alone: the required check ships as
`@pytest.mark.xfail(strict=True)` naming this entry, so it fails the build the
day the property starts holding and nobody has come back here.

## T4-2 · `db.py` has one line of headroom and Task 4 asks it for fourteen delegations · owner: decision gap

**Symptom.** Task 4's `Produces` ends "**Store (db.py) gains thin delegations
with the same names**", and its Files/Surfaces budgets "~15 lines" for them.
`src/shepherd/store/db.py` is **599** lines against ADR-1's **600**-line cap,
which `test_no_source_file_exceeds_600_lines` enforces. Fourteen delegations are
twenty-eight lines at two lines each (`def` + body), so the budget is over by
thirteen lines before the cap is considered, and over the cap by twenty-seven.
The two sentences cannot both be satisfied.

**What was tried.** The three shapes that would fit were each rejected:
(i) calling `Store._write` from `sessions.py` / `mailbox.py` — Task 4's
Out-of-Scope Drift names this exactly ("Reaching into `db.py`'s internals rather
than taking the connection it hands over");
(ii) mixins (`class Store(SessionVerbs, MailboxVerbs)`) — three lines, which
still exceeds the one line available, and it moves `Store`'s surface into files
whose `self` is untyped against it;
(iii) reclaiming lines inside `db.py` — a refactor of shipped M1/M2 code, which
is out of this phase's scope and exactly the "quiet edit" the task forbids.

**What it blocks.** T11 (`create_owned_session`, `set_runner_handle`,
`owned_session_counts`, `children_of`), T12 (`rebind_engine_session_id`), T14
(all six mailbox verbs), T15 and T20 — every one of them consumes these verbs
through a `Store`, and no `Store` method exists to reach them. The verbs
themselves are built, tested and green at the connection seam; what is missing is
the delegation layer.

**Decision.** Where do the `Store`-level delegations live, given that `db.py`
cannot hold them?

**Pressure.** ADR-1's cap exists because logic hides in long files, and it has
already forced two healthy splits (`rows.py`, `stops.py`). D33 pushes the other
way: callers get **verbs on the store**, never a connection, and the connection
must not escape `store/`. Both are load-bearing and this task cannot honour both
with the shape `Produces` names.

**Options.**
1. **Delegation mixins in the sibling modules.** `sessions.py` and `mailbox.py`
   each gain a small `…Verbs` class whose methods call `self._write` /
   `self._read`; `db.py` changes by exactly one line
   (`class Store(SessionVerbs, MailboxVerbs):`) plus one import line — still two
   lines over, so it needs either one line reclaimed in `db.py` or the cap
   raised for this file by name.
2. **A third sibling, `store/verbs.py`**, holding a `Store` subclass or a
   delegation façade, with `open_store` returning it. `db.py` gains nothing; the
   public name callers import stays `Store`, re-exported.
3. **Raise ADR-1's cap.** Rejected here on sight: the cap is the reason this
   split happened at all, and raising it to avoid a split is the failure it was
   written against.
4. **Split `db.py` first** (the M1/M2 read verbs into `store/reads.py`), then let
   it hold the delegations. Correct long-term, and a refactor of shipped code
   that no M3 task owns.

**Recommendation (NOT applied).** Option 2, because it adds no line to `db.py`,
keeps the connection inside `store/`, and leaves `Store` the single name callers
import. **Nothing is built for it**: `db.py` is unchanged except for two
same-line column-list edits (below), and the verbs are reachable today only at
the connection seam, which is where T4's own tests exercise them. The first task
that consumes a verb through a `Store` is blocked until this is settled.

**One thing was changed in `db.py`, and it added no line.** `SESSION_COLUMNS` and
`fleet()`'s column list now project `runner_handle`, `title_synced_at`,
`parent_session_id` (and `depth` for the fleet) — the columns Task 4's
Files/Surfaces says `Session` and `FleetRow` gain, which "already exist and are
not yet projected". Both edits extend an existing string line, so `db.py` is
still **599** lines. Recorded here rather than left as a quiet edit.

## Router decisions on T4-1 and T4-2 · 2026-09-17

### T4-1 — **option 1: split the verb.** Two intents, two verbs.

`bind_engine_session_id(connection, session_id, id)` binds an **unbound** row;
`rebind_engine_session_id(...)` performs C14's **move**. T15 consumes the first,
T12 the second. I am widening T15's stated `Consumes` by one name, explicitly and
here, rather than leaving a builder to do it quietly — which is the rule the plan
protects, and the reason this entry exists at all.

**What decides it is the builder's own finding, which is worth more than the
decision.** A compare-and-set cannot express "exactly once" under D37: one writer
means the transactions serialise, so every caller reads the value the previous one
committed and every CAS matches. The recorded run says so — *"exactly one bind may
win, not ['fork-1', 'fork-0', 'fork-3', 'fork-4', 'fork-5', 'fork-2']"*. So the
property was not merely untested; with one verb carrying C14's semantics it was
**unreachable**, and the test named for it could only ever have asserted something
weaker while keeping the stronger name. That is this repo's dominant defect, and
it was caught before it shipped rather than by a reviewer three milestones later.

The split makes the property reachable by the mechanism **T4 already proved works
in this very task**: a conditional write that reports its own rowcount. Exactly as
`mark_delivered` guards delivery-once with `AND delivered_at IS NULL` and returns
`cursor.rowcount`, `bind_engine_session_id` guards with
`AND engine_session_id IS NULL`. The condition is evaluated *inside the write*, so
serialisation is what makes it correct rather than what defeats it. The second
binder updates zero rows and is told so.

The strict xfail stays until the split lands, then becomes a real test.

### T4-2 — **option 4: split `db.py`.** The cap is doing its job; take the split.

Move the M1/M2 **read** verb implementations out of `db.py` into `store/reads.py`,
leaving thin delegations behind; the reclaimed lines then hold Task 4's fourteen.
`Store` stays the single name callers import, D33's "verbs on the store, never a
connection" is preserved exactly, and the connection never leaves `store/`.

I am rejecting the recommendation (option 2) and option 3, for the same reason:
**`db.py` is at 599 because it is doing too much, and that is precisely what the
cap is for.** Raising it, or routing around it with a façade in a third module,
both answer "the file is full" with something other than emptying the file. This
repo has taken that lesson three times already and been right each time —
`rows.py` and `stops.py` were both cap-forced splits, and this morning
`signals/rules.py` sat at 600/600 and was fixed by moving its ten field readers
into `signals/fields.py` rather than by raising K4. I told that builder *"do not
raise the cap; the cap is the signal that the file is doing too much."* The same
answer holds here and consistency is part of why the rule keeps working.

On "no M3 task owns this refactor": that is an ownership question, not a
correctness one, and the router can assign ownership. It is a mechanical move
guarded by 100 store tests and a 1000-test suite — the cheapest kind of refactor
this codebase will ever be asked for, and it gets cheaper never.

## T8-2 — `check_tmux_argv` recognises the binary by **spelling**, and an absolute path defeats it

**Status: OPEN, DECIDED, fix authorized. Found by the router, 2026-09-17, verifying T8's own fix
by hand rather than trusting its tests.**

T8 found and closed a real hole: `check_tmux_argv` deliberately returns early on an argv whose
`argv[0]` is not tmux ("a guard that polices `git` gets turned off"), and `ensure_server` prefixes
the launch with `DetachedLaunch.prefix` (DP5) — so a wrapper was a hole exactly as wide as the
wrapper. `make_run_argv` now checks twice, the second time through `_tmux_tail`, which re-presents
the argv from the binary onward. **That fix is correct and I verified it directly.**

Verifying it also showed it does not go far enough. Run against the shipped guard:

```
bare kill-server on the user's socket      1-check=REFUSED   2-check(shipped)=REFUSED
systemd-run wrapper (the hole T8 found)    1-check=THROUGH   2-check(shipped)=REFUSED
wrapper whose own flag value is 'tmux'     1-check=THROUGH   2-check(shipped)=REFUSED
setsid wrapper                             1-check=THROUGH   2-check(shipped)=REFUSED
ABSOLUTE tmux path, no wrapper             1-check=THROUGH   2-check(shipped)=THROUGH   <-- reaches `shepherd`
ABSOLUTE tmux path behind a wrapper        1-check=THROUGH   2-check(shipped)=THROUGH   <-- reaches `shepherd`
```

`["/usr/bin/tmux", "-L", "shepherd", "kill-server"]` passes **both** checks and reaches the user's
live sessions. Both gates test the binary by string equality against `VERSION_ARGV[0]` — `argv[0]
!= "tmux"` in the guard, `word == BINARY` in `_tmux_tail` — so any path spelling walks past.

**This is acceptance clause 1's own words failing.** The clause requires that *"the guarantee is on
the argv, not on a spelling."* `argv[0] == "tmux"` **is** a spelling.

**It is not reachable today and that is not much comfort.** Nothing in `src/` resolves tmux to a
path; every argv is built from `VERSION_ARGV[0]`. But **C1 in `implementation-constraints.md` says
a systemd unit calling a bare name exits 127 and to "use an absolute path"** — and DP5's
`DetachedLaunch` *is* the systemd wrapper. The one documented constraint most likely to be applied
to this exact code path is the one that silently disarms the guard, and the failure mode is that
nothing looks different: no test goes red, and the next `kill-server` lands on `shepherd`.

### Decision — recognise the binary by **basename**, keep matching the flags by equality

Prototyped and verified before writing this down:

- `_is_binary(word)` is `PurePosixPath(word).name == VERSION_ARGV[0]`. Both gates use it:
  `check_tmux_argv`'s early return, and `local.py`'s `_tmux_tail` scan.
- A recognised argv is re-presented under the canonical name before the socket / `-t` /
  `kill-server` rules run, so those rules are unchanged and keep their existing tests.
- The `-V` allowance keeps its equality match **on the flags** (`tuple(argv[1:]) ==
  VERSION_ARGV[1:]`), so it stays the narrow exception clause 1 describes rather than becoming a
  prefix match — the thing T5 was careful about.

Measured against the shipped guard, this refuses `/usr/bin/tmux`, `./tmux`, and both behind a
wrapper, while every legitimate argv still passes: permitted socket bare **and** absolute, `tmux -V`
bare **and** absolute, and a non-tmux program (`git`) still correctly left alone.

**Not chosen: refusing an absolute path outright.** It is simpler, and it would break C1's own
remedy the day the runner legitimately needs an absolute binary under systemd. Widening
*recognition* is strictly the safe direction — the guard polices more argvs, never fewer.

This is a **correction, not a reversal**: ADR-M3-8 and clause 1 are unchanged, and the fix is what
they already say. No decision among the 54 moves.

**Required proof:** the six-row table above, as a test, with the two absolute-path rows proved to go
red against the pre-fix guard. A planted `["/usr/bin/tmux","-L","shepherd","kill-server"]` must be
refused at `make_run_argv`, and the test must live in the default `-m "not live"` sweep (clause 1
requires the blast-radius rule run there).

### What happened

T10's code reviewer planted 16 mutations into `src/shepherd/engines/claude_code/spawn.py`. One was

1. **The router dispatched two mutation-planting agents at the same file concurrently.** The

2. **A hash was reported instead of compared.** Computing the expected value and printing it is not
   verification; the comparison has to be a command whose exit code decides.
3. **The dangerous default did the damage.** `trust_state(cwd, engine_config_home=None)` defaults to

1. **Only one agent may hold write access to a given file at a time.** The router must not dispatch
   a second planting agent — reviewer, hunter, or builder — at a file another agent can write.

2. **Restoration is proved by a command that fails, not by a printed hash.** Record
   `sha256sum <file> > <backup>.sha` *before* the first plant, and finish with

3. **Never plant a mutation in a code path whose default target is a real user file.** Redirect it

   redirect holds before planting anything.
4. **The router verifies, it does not accept.** Every agent report ends with the suite actually run

   caught by reading.

## T10-R2 — router decisions on the merged T10 review + hunt findings · 2026-09-17

Two independent agents audited T10. They agree on the one defect that ships broken, and between

### The defect that ships broken — the byte ceiling is measured on the wrong string

Both agents found it independently and both reproduced it against **real tmux 3.4**:

```
spawn_argv ACCEPTS a 16261-byte brief; its own accounting = 16324 <= 16324
real client->server command = 16430 bytes (106 bytes of framing spawn_argv never counted)
tmux rc=1 stderr='command too long'
with 10 env vars: real command = 17020 bytes -> 'command too long'
```

`command_size` sums only the `claude` argv. `LocalRunner.start` prepends
`new-session -d -s <name> -c <cwd> -x <cols> -y <rows> [-e K=V]*` and tmux's limit applies to the
whole client→server message — proven by the hunter's cleanest experiment: **adding 55 bytes of
frame moved the largest accepted argument by exactly 55** (16325 → 16270).

A10/E-M3-10's words are *"the brief plus the rest of the command"*. This is the rest of the command.
Worse than a missed refusal: `local.py`'s `_checked` raises `RunnerRefusal(f"... {list(words)!r}")`,
so the operator gets the entire 16 KB brief interpolated into the exception text, and `spawn.py`'s
own *"shorten it by N bytes"* advice undershoots by the frame width, so following it retries and
fails again. The existing test enshrines the wrong model — correct arithmetic over an incorrect
frame.

**Decision — the runner's fact is injected, exactly as `capabilities()` already does it.**
`spawn_argv(spec, binary, *, frame_bytes: int)`. `LocalRunner.start` computes `frame_bytes` with
`command_size` over its **own** prefix words **including every `-e K=V` env word** — `spec.env` is
unbounded and ten modest vars alone put it 696 bytes over. `command_size` joins `__all__`; it is the
function the caller now needs. **Not chosen:** moving the budget into `runner/`. The actionable
message needs the brief, and the brief is the engine's. The engine keeps the message and stops
owning a number it cannot see.

**Required proof:** a test that takes the **full `new-session` word list** at the accepted boundary
and asserts it is ≤ `TMUX_COMMAND_LIMIT_B`. It goes red on today's code.

```
THROUGH  ['/usr/local/bin/tm','-L','shepherd','kill-server']
REFUSED  ['/usr/bin/tmux','-L','shepherd','kill-server']          <- T8-2's fix, holding
```

**Class 1 — the binary inside a single word.** Both gates scan argv *elements*. `sh -c "<whole
command>"` puts the entire invocation in one element whose basename is the whole string, so nothing
matches. The `run-shell` and `new-session <cmd>` rows are the same hole reached through a
**permitted** socket: the socket is legal, and `"kill-server" in argv` is a membership test over
elements, so a payload word *containing* the verb never matches it.

This is not hypothetical. C4 says tmux runs a single command string through `sh -c`, and
**`LocalRunner.attach` already builds exactly that shape** — `local.py:322`,
`self._checked("pipe-pane", "-o", "-t", spot, f"cat >> {sink}")`. It is the production idiom.

**Class 2 — a symlink or renamed copy.** `tm -> tmux` is invisible to `PurePosixPath`, which is
lexical by design (the predicate is pure, and the plan forbids `os` in it). Closing it needs
filesystem resolution and therefore trades that purity.

### Why this is not blocking M3

**Nothing in `src/` builds either shape today.** Every tmux argv goes through `_checked`, and the
one command-bearing argument the product does construct — `pipe-pane`'s sink — is already confined
by `SINK_PATH_RE` (`local.py:316`), precisely because C4 says it is re-read by a shell. So this is
defence in depth, not a live hole, and it is being recorded rather than rushed.

### Decision — constrain the command-bearing arguments; do not blanket-scan words

1. **Enumerate the shell-executing verbs** (`run-shell`, `if-shell`, `new-session`, `new-window`,
   `split-window`, `respawn-pane`, `respawn-window`, `display-popup`, `pipe-pane`) and require their
   command argument to match a narrow allow-list, the way `SINK_PATH_RE` already does for
   `pipe-pane`. That generalises a mechanism this repo has already proved rather than inventing one.
2. **Allow-list `argv[0]` at the exec site.** It may be the binary, or a wrapper from
   `DetachedLaunch.prefix` — never a shell. `sh -c` reaching `make_run_argv` is itself the anomaly.
3. **Class 2 stays open and is written down as such.** Resolving symlinks makes the predicate impure
   and buys defence against an attacker who can already write to `PATH` — at which point the guard
   is not the control that matters. Recorded as a named gap, not silently accepted.

**Explicitly rejected: "no argv word may contain the binary's name."** It is the obvious rule and it
is wrong — `spawn_argv` puts the operator's **brief** in an argv word, so a session briefed *"fix
the tmux bug"* would be refused. A guard with false positives on ordinary work gets turned off, and
ADR-1's "an exemption is how boundaries die" is the same lesson from the other end.

## T9-1 — `Runner.snapshot(handle, lines)` does not say what `lines` counts. **DECIDED.**

T9's builder found the seam undecided and, correctly, asserted only what the seam *had* decided
(bytes, undecoded, escapes intact) rather than picking a winner in a test:

- `base.py` says "the last `lines` rendered rows".
- `LocalRunner` sends `capture-pane -e -p -S -<lines>`, which is `lines` of **scrollback** *plus*

depth, not a length. Making `base.py` say "rendered rows" match `ScriptedRunner` would put the seam

`LocalRunner` is right and the **prose** was wrong — no decision among the 54 moves, and no
production behaviour changes.

`ScriptedRunner` changes to match: it returns its scrollback-depth rows plus its visible rows. The
contract suite gains a row asserting the parameter's meaning in both implementations, and it must go

**It is worse than "a corner case", and the spec says so in two places.** The schema's own column
note reads: *"`root_path` … only where `discover_repos` starts looking; repos may live anywhere
(D22)"* (`orchestrator-platform.md` l.647). And D22's rationale ties the allowlist to repos
explicitly: *"`add_repo` is `local_destructive` because §13 validates every spawn against the
registered allowlist — adding a repo **widens that allowlist**."* So the allowlist's population is
**registered repo paths**, and T11 is reading the one column the spec says is not where repos are.
It is not an edge case; it is the normal case for any repo not nested under its workspace root.

**Refusing is the safe direction and nothing unsafe shipped** — the failure is availability, not
authority, which is why this is not blocking.

**Note on D48, so the next reader does not misread it:** D48 revises how a session *binds* to a repo
(`git rev-parse --git-common-dir`, not longest-prefix match). It does **not** revise what §13's
allowlist is made of. Binding and admission are two questions; D48 answers the first and D22 answers
the second. Do not "simplify" this by deciding D48 removed the prefix match from §13 as well.

### Decision

1. **`store/` gains a read verb enumerating registered repo paths** — `list_repos(workspace_id)`,
   or a tree-wide `registered_roots()` if the caller never needs them grouped. It belongs with the
   other read verbs in `store/reads.py`, delegated from `Store`, per D33.
2. **`orchestration/admission.py` validates `cwd` against those repo paths by longest-prefix match**,
   resolving to the **innermost** match (D22's own words), with the workspace `root_path` kept as an
   additional permitted root where it is not `NULL` — a workspace root is also registered, so
   dropping it would narrow the allowlist in the other direction.
3. **The existing refusal tests stay.** `test_a_workspace_with_no_registered_root_refuses` and the
   traversal test are both still right; they gain a sibling proving a repo **outside** its
   workspace's root is now admitted, which is the case that is broken today and must go red against
   the current code.

### Two tmux facts were measured on this host, not assumed (socket `shepherd-m3-t83`, torn down)

Both decide how the guard has to be written, and both were checked before a line of it was:

```
$ tmux -L shepherd-m3-t83 display-message -p one ";" display-message -p two   → one / two   (rc 0)
$ tmux -L shepherd-m3-t83 display-message -p "one;" display-message -p two    → one / two   (rc 0)
$ tmux -L shepherd-m3-t83 display-message -p "a;b"                            → a;b         (rc 0)
$ tmux -L shepherd-m3-t83 display-message -p one "\;" display-message -p two  → rc 1, "too many arguments"
```

A word that **is** `;` starts a new tmux command, and so does a word that **ends** in `;` (the `;` is
stripped); a `;` mid-word does not, and `\;` is a literal. So a shell-executing verb can sit behind a
separator after a verb the guard finds boring — `send-keys … ";" run-shell '<payload>'`. The guard
therefore scans **every segment**, not the first (mutation M9).

```
$ tmux -L shepherd-m3-t83 new-session -d -s one 'sleep 60 && echo x'   → pane pid cmdline: bash -c sleep 60 && echo x
$ tmux -L shepherd-m3-t83 new-session -d -s two sleep 60               → pane pid cmdline: sleep 60
```

C4's *"a single command string is run through `sh -c`"* is exact, and the manual's l.429–438 is right
that **multiple** arguments are executed directly. The allow-list is applied in **both** cases
anyway: the multi-word form still execs a program of the caller's choosing, and
`new-session … /bin/sh -c '<payload>'` is the multi-word form of the single-word hole.

### The allow-list, and why each member is on it

The allow-list is **injected at the exec site**, `permitted_commands(...)` → `make_run_argv(permitted,
commands)` → `check_tmux_argv(argv, permitted=, commands=)`, exactly as `permitted_sockets` is.
Required, never defaulted: an optional safety argument is the shape of a check that never runs
(T6-2, and the `capabilities` degrade that never fired). There is **no module-level default set**,
for the reason `permitted_sockets` has none — a default would fix the members at import time.

| member | why it is on the list |
|---|---|
| `cat` | The one command this product composes. `LocalRunner.attach` builds `pipe-pane -o -t <target> 'cat >> <sink>'` (`runner/local.py:323`), and the sink is already confined by `SINK_PATH_RE` for this very reason. `cat` appends bytes to a path and starts nothing. |
| the engine's binary (`claude`) | `new-session`'s command words are `spawn_argv(spec)`'s. It is **not spelled in `runner/`**: T8-1 already established that `runner/` may not carry engine vocabulary, which is why `spawn_argv` is injected into `LocalRunner` — the allow-list is injected for the same reason, and a second engine changes a composition-root argument rather than a constant in the multiplexer driver. |

Nothing else. Not `sh`, not `bash`, not `env`, not `systemd-run`: an argv that needs a shell *inside*
a tmux command argument is the anomaly, which is decision 2's own sentence applied one level in.

**`argv[0]` of the command is matched by basename** (`/bin/cat` is `cat`; `mycat` is not), the same
predicate T8-2 established for the tmux binary, and **the whole command argument is confined to
`COMMAND_ARG_RE = ^[A-Za-z0-9_./ >=:,+-]*$`**. The second half is not decoration: `cat >> /x ; <payload>`
passes an `argv[0]` allow-list *by construction*. `>` is in the charset because `cat >> <sink>` needs
it; `;`, `&`, `|`, `$`, a backtick, a quote and a bracket are not, because each one turns one
permitted program into a second unlisted one. Positive charset, like `SINK_PATH_RE` — a deny-list of
metacharacters is a list of the ones its author thought of.

### The `invoke()` question, answered rather than left to the next reader

T23's handoff asked, in writing, whether `invoke()` flattening an unexpected exception into
`Failure.FAILED` + the exception's class name is correct at that seam, or a second defect.

**It is correct behaviour at that seam. It is not a second defect, and it should not be
changed.** `registry.py:247`:

```python
except Exception as error:  # noqa: BLE001 - a traceback never reaches the caller
    return _failure(ctx, name, Failure.FAILED, type(error).__name__)
```

Four reasons, in the order they matter:

1. **`FAILED` is not a mislabel; it is the truth about what happened.** The tool *did* crash.
   `Failure.REFUSED` means "your argument was rejected", `UNAVAILABLE` means "not here, not
   for you"; a verb that raises is neither. Reporting a crash as a refusal is the *inverse*
   of the defect principle 5 forbids — it would make a page unable to tell a refusal from a
   crash by laundering crashes into refusals, permanently, for every tool.
2. **It cannot do better without guessing.** A generic handler sees `ValueError` and has no
   basis to decide whether that is an expected refusal or a defect. Every classification rule
   it could apply is a guess, and a guess that reads like a fact is exactly what this repo
   refuses one layer down (`check_tmux_argv` "refuses, never repairs"; `admit` "refused, never
   guessed at").
3. **It already does the things a backstop at a trust boundary must do**: no traceback
   reaches the caller (§13 Errors), the generic literal is returned with a correlation id, and
   the class name is recorded in `resolve_failure`'s ring so the id the user is shown resolves
   to something an operator can read. That is how the defect was findable at all.
4. **The projection is the verb's job, and that is where it was fixed.** `SpawnRefused`
   already exists, `spawn_owned_session` already returns it, and the tool handler already
   projects it. The only thing wrong was that `admit` raised past all of it.

**What would be a real defect at that seam** — and is not the case here — is `invoke()`
swallowing the exception *silently*, or returning `ok=True`, or letting the class name reach
the caller. None of those happens. Recorded so the next reader does not re-open it: no task
is filed, and `toolsurface/registry.py` was not touched.

### F3 — `controld.stop()` treated a hung thread as an exited one · CLOSED

`thread.join(timeout=…)` returns `None` whether the thread exited or the timeout

guard*), it went to a new **`src/shepherd/daemons/shutdown.py`** (71 lines) and

`return shut_down(running.threads, running.store.close, JOIN_TIMEOUT_S)`.

and `RESERVED_FOR_M2` are untouched at 150/10, both spellings.

**What a hung thread now produces.** `stop()` returns a frozen `ShutdownOutcome`
(`joined`, `hung`, `store_closed`, `timeout_s`) and `main` prints it on the way

rather than asserted against its source, because the claim is that a human
running `shepherd-controld` sees it:

* every thread exited → `controld stopped: 3 threads exited · store closed`
* one did not → `controld stopped: 1 of 3 threads did not exit within 10.0s and

1. **`store.close()` is skipped while a thread is unknown.** `Store.close()`
   drains the write queue and joins its writer with **no timeout**, so closing
   under a thread that is still enqueueing writes trades a visible unknown for an
   invisible hang. The process is exiting either way and SQLite's durability does
   not depend on a clean `close()`. The outcome says the store was left open, so
   the skip is reported, never silent. Load-bearing: m10.
2. **No new `AnomalyKind`, and the file was read before deciding.**

   with no writer and no reader. It goes where shutdown can actually be seen —
   the process's own exit line. (`doctor` cannot report the shutdown of the
   daemon it talks to.)

The exit code is still `EXIT_OK` when a thread hangs. Displaying is what
principle 5 asks for; turning a shutdown observation into a process failure is a
policy nobody has decided, and inventing one here would be the quiet kind of
change this ledger exists to stop.

**No decision pressure.** D51 (own the framer) is untouched; T19-c is reaffirmed

1. **A planted violation is an inert fixture that nothing imports.** It lives in

3. **Never plant a signal, a `kill`, a reboot-capable call, or a teardown verb into executable code

4. **The runtime net is not a substitute for rules 1–3.** It is the backstop for the class of mistake

### Finding 1 — `check_tmux_argv` enforced §18's verb by a **spelling**. CLOSED.

`if "kill-server" in argv` is a membership test over **one** of eleven words that reach that command.
**tmux resolves an unambiguous command-name prefix.** Measured on this host at this remediation
(tmux 3.4, socket `shepherd-m3-remfix`, torn down, `no server running` confirmed):

```
tmux -L shepherd-m3-remfix new-session -d -s probe_a 'sleep 300'   -> probe_a: 1 windows
tmux -L shepherd-m3-remfix kill-s      -> rc=1  "ambiguous command: kill-s, could be: kill-server, kill-session"
tmux -L shepherd-m3-remfix kill-serv   -> rc=0  ls: no server running
tmux -L shepherd-m3-remfix kill-serve  -> rc=0  ls: no server running
```

**Blast radius, stated exactly.** The user's `shepherd` socket was unreachable by every spelling,
because the socket rule is tested *before* the verb rule. What a prefix reached was
**`shepherd-runner` — the product's own server, i.e. every owned session at once.** A new
`LocalRunner` method issuing `self._checked("kill-serv")` — spelling no `tmux` literal, going through
the product's own argv builder — **survived the entire 1470-test default suite** (verified by
re-running it here before the fix).

**What made it the milestone's signature defect:** `tmux_cmd.py` already knew the rule. `_shell_verb`
matches prefixes and aliases, and **its own docstring** says that matching full names only "would be
the same class of mistake as `argv[0] == 'tmux'` (T8-2): a spelling, not a property." The lesson was
applied to the shell verbs and not to the one verb §18 is about.

**What this host's manual says, read rather than remembered** (`man tmux`, tmux 3.4):
`kill-server` takes no options and carries **no `(alias: …)` line** — unlike `kill-pane` (`killp`),
`kill-window` (`killw`) or `list-sessions` (`ls`). So its own name and its prefixes are the entire set
of words that reach it. `KILL_SERVER_ALIASES` is therefore `()` — empty **as a measurement**, with the
manual cited, so the day a tmux version gives the verb an alias there is one place that fact goes.

**The rule as written** — `is_server_teardown(word)`, pure, argv in, refusal or nothing out:

* True for every non-empty prefix of `kill-server`, and for any prefix of any alias (none today).
* **Ambiguous prefixes are refused too**, on purpose. `kill-s` is also a prefix of `kill-session`, so
  tmux answers `ambiguous command` and does nothing. Refusing it costs an argv tmux would have
  rejected anyway; the alternative is mirroring tmux's whole command table in the predicate, a copy
  that goes stale in silence. **Refusing is the safe direction: wrong in it costs a refusal, wrong in
  the other direction costs every owned session at once.**
* **Position is the caller's job.** The rule runs on the **first operand of each command in the
  argv**, after that command's own server-region flags, which is the only place tmux prefix-resolves.
  `_segments` is why a teardown behind `;` is looked at rather than hidden behind a first allowed
  verb. A word that merely *contains* the verb is not a command-name position — `spawn_argv` puts the
  operator's brief in an argv word, and *"no argv word may name the teardown"* is the rule **T8-3
  rejected out loud**, because a session briefed "fix the kill-server bug" would be refused and a
  guard with false positives on ordinary work gets turned off.
* The **literal** membership test is kept as the cheap second layer, unchanged, covering the
  positions the property deliberately does not look at. Two layers, the way the cross-origin check
  and the handshake check each cover a different half.
* It **refuses, never repairs**: proved by mutation, below.

**The verb list checked for false positives — read off `runner/local.py`, not from memory.** Every
verb the product issues: `has-session`, `new-session`, `kill-session`, `send-keys`, `capture-pane`,
`pipe-pane`, `set-option`, `display-message`, `list-sessions`/`ls`. **None is a prefix of
`kill-server`** — `kill-session` diverges at the sixth character. `test_no_verb_this_product_issues_is_a_prefix_of_the_teardown_verb`
asserts both halves: every one of them is allowed, and none of them is a prefix.

**`is_server_teardown` is public**, and that is the design decision worth recording:
`tests/boundaries/test_tmux_blast_radius.py` reads the **same function**, so the runtime net and the
edit-time net cannot drift into disagreeing about what the verb is. *A second definition of a
property is how a property becomes two spellings.*

**The edit-time net had to move too, and this is the part the runtime fix alone would not have
closed.** MUT-G4's method is never called, so no runtime predicate can fire on it; only a scan of
