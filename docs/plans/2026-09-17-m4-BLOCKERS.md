## T1-1 · Step 0b row 10's command produces file counts, not node ids, so acceptance clause 16 has no baseline as written · owner: plan correction, worked around in place

**Symptom.** Step 0b row 10 says to run
`.venv/bin/pytest --collect-only -q > tests/boundaries/collected_node_ids.txt` and calls the result
"the baseline clause 16 subset-compares against". Run verbatim on this tree it writes **116 lines**
of `path: count`, containing **zero** `::` node ids:

```text
tests/boundaries/test_capability_degrade.py: 11
tests/boundaries/test_composition_root.py: 2
```

**Cause, and it is a two-line fact worth keeping.** `pyproject.toml:49` already sets
`addopts = "-q -m 'not live'"`. The `-q` on the command line is therefore the **second** `-q`, and
pytest 9.1.1 collapses `-qq --collect-only` to a per-file count summary. A set of file counts cannot
be subset-compared for a deleted or renamed test, which is exactly what clause 16 exists to detect.

**What was tried.** `--co-format=id` is not a pytest 9.1.1 flag. The command that does produce node
ids on this tree keeps a single `-q` by replacing `addopts` rather than adding to it:

```text
.venv/bin/pytest --collect-only -q -o addopts="-m 'not live'" > tests/boundaries/collected_node_ids.txt
```

which writes **1480** node ids and the trailer `1480/1517 tests collected (37 deselected)`. That is
the file committed at
`tests/boundaries/collected_node_ids.txt`, and it matches step 0b row 1's expected 1479 passed +
1 skipped.

**What it blocks.** Nothing now — the baseline exists and is correct. It is recorded because the
**plan's own deciding command is wrong**, and clause 16's whole point (revision 2 added it because
revision 1 "had no deciding command at all") is defeated by a command that cannot fail. **Clause 16
and step 0b row 10 must be corrected to the `-o addopts=` form before acceptance**, or the next
builder re-freezes counts and the subset compare silently passes forever.

## T7-3 · `module_imports` is blind to call-shaped imports, and fifteen shipped rules use it bare · owner: evidence gap, measured, NOT fixed here

**Symptom.** Measured on this tree:

```
$ .venv/bin/python -c "...module_imports on a file containing
   importlib.import_module('claude_agent_sdk'); __import__('mcp')"
['importlib']
```

`importlib.import_module("x")` and `__import__("x")` are **`ast.Call` nodes, not
import nodes**. Every boundary rule that resolves imports through
`module_imports` alone — the consumer boundary, the layer direction rule, the
storage boundary, the hookd isolation rule, and the rest of
`tests/boundaries/` — reports a module using those spellings as clean, while
the module is loaded and the cost is paid identically. This is the same class as
M3's K16 lesson ("a rule keyed on one exact spelling"), one node type over.

**What T7 did.** Added `dynamic_import_targets()` (callee resolved through
`_alias_origins`, so `from importlib import import_module` is seen; argument
resolved through module-level string constants, which is how the spelling is
idiomatically written) and `all_imports() = module_imports | dynamic_import_targets`.
**Both new rules (DP3, DP4) use `all_imports`, and each ships a fixture for each
form**: `toolsurface_logs_via_import_module.py` and
`toolsurface_imports_the_vendor_sdk_dynamically.py`.

**What T7 deliberately did not do.** `module_imports` itself was **not** widened.
Changing the walker under fifteen live boundary rules — while three sibling
builders are writing to `src/` — is not this task's to take, and a widening that
turns a sibling's in-progress module red is indistinguishable from a real
finding.

**What it blocks.** Nothing at M4. **Owner: whoever next touches
`tests/boundaries/_imports.py` on a quiescent tree.** The one-line change is
`module_imports` → `all_imports` inside `consumer_violations`,
`direction_violations`, the storage rule and the hookd rule; the fixtures to
prove it already exist.
