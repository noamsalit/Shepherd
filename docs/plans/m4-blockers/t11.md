## T11-1 · `tools_list_payload` ships with **no caller in the build**, because Tasks 12–15 were cut · owner: recorded, shipped per the plan, not resolvable by T11

**Symptom.** T11's Produces block names four functions. Three have a consumer on the graph:
`exported_tools` and `call_exported` are T16's (`toolsurface/client.py`), and `result_payload` is
what `call_exported` is built from. **`tools_list_payload` has none.** Its only possible consumer was
the tier-2 stdio binding — `to_stdio_mcp_server` / `mcpsrv/stdio.py` — and the plan cuts it three
paragraphs below Task 11 ("Tasks 12–15: **CUT at revision 2**"), for a reason it states plainly:
`invoke()` discards the caller, so `SESSION`-audience tools cannot be scoped to the session calling
them. The master binding (T20) does not consume a `tools/list` payload either: it consumes
`ExportedTool` and hands the schema to `@tool`, and `create_sdk_mcp_server` builds the wire entry
itself.

**What was tried.** Nothing was removed. The plan's Produces block is binding and the shape is
captured, so the function ships **tested** rather than shipping absent or shipping untested. But the
plan's own sentence about the cut — *"shipping a translator nothing calls is M3's T25/F1 defect"* —
applies to this function as much as to `to_stdio_mcp_server`, and the reason it survived the cut is
most likely that it is one line inside a task the cut did not re-read.

**What it blocks.** Nothing. **Owner: whoever builds the tier-2 binding** (post-M4, after per-caller
scope exists). If that binding never arrives, `tools_list_payload` should be deleted with the same
reasoning that deleted `to_stdio_mcp_server`, and this entry is the note that says so out loud rather
than leaving a reader to wonder who calls it.

## T11-2 · Nothing in this tree can produce a denial, so `DENIED_TEXT` is a literal with no producer — and its **second** speller is T4 · owner: handoff to T4 / whoever widens `invoke()`

**Symptom.** T11's required check asks for *"the encoded result for a denial, a refusal and a
failure"*. Refusal and failure are reachable from `invoke()` today (`Failure.REFUSED` when a handler
raises `ToolArgumentRefused`, `Failure.FAILED` when it raises anything else). **A denial is not.**
§11's gate (`authorize()`) is not behind `invoke()` in this tree yet, and `Failure` has three members
— `UNAVAILABLE`, `REFUSED`, `FAILED` — none of which means *a human declined*.

So the denial half of that check is proved by handing `result_payload` a `ToolResult` the *future*
gate will build (`ok=False`, `error=DENIED_TEXT`), which is an honest proof of the **encoder** and is
not a proof that anything produces one.

**The part that is a live hazard, not just an absence.** Task 4's `build_authorizer` returns
`AuthzOutcome(allowed=False, reason=…)`, and whoever widens `invoke()` turns that `reason` into the
`ToolResult.error` this module encodes. **That makes `approvals.py` the producer of the denial text
and `export.py` the declarer of it** — two modules, one literal, which is the shape D32 removed three
hand-maintained lists to prevent. `DENIED_TEXT` lives in `export.py` because T11's Produces block puts
it there; the rule that keeps it from drifting is that T4 (or the `invoke()` widening) **imports**
`shepherd.toolsurface.export.DENIED_TEXT` rather than spelling `"you declined this"` a second time.

**What it blocks.** Nothing in T11. **Owner: T4 and whoever widens `invoke()` with the gate.** If a
second spelling does ship, the cheap rule is a scan asserting the literal appears in `src/` exactly
once — the shape `test_the_prefixed_name_is_only_spelled_here` uses for `mcp__shepherd__` in T20.

## T11-3 · The `tools/list` key is camel (`inputSchema`) and the snake spelling has **no capture** · owner: decision, recorded with its evidence

**Symptom.** `data-schemas.md`'s rule is that no shape may be asserted without a real example.
Two spellings were candidates for `tools_list_payload`'s schema key: our own `input_schema` (which is
`ToolDef`'s and `ExportedTool`'s field name) and the wire's `inputSchema`.

**What was measured.** Every captured `tools/list` entry — in-process (§In-process MCP `initialize`
and `tools/list`: `{"description": …, "inputSchema": {"properties": {}, "type": "object"}, "name":
"fleet_summary"}`) and tier-2 stdio (§Tier-2 stdio MCP: `{"name": "echo_note", …, "inputSchema":
{...}}`) — spells it **`inputSchema`**. There is **no capture anywhere** of a `tools/list` entry
carrying `input_schema`, so the snake spelling would have been a shape asserted without an example.

**And it is not a vendor shape (D32, DP4).** `inputSchema` is MCP's, not `claude_agent_sdk`'s: the two
captures come from two different clients (the in-process SDK server and Claude Code's stdio client)
and agree. The vendor vocabulary D32 bans from L4 is the SDK's own — `create_sdk_mcp_server`, `@tool`,
`McpSdkServerConfig`, the `mcp__shepherd__` prefix — and none of it appears in this module, which is
asserted by `test_export_imports_no_vendor_package` and by
`tests/boundaries/test_l4_import_rules.py::test_no_vendor_sdk_below_l5`.

The call **result** keeps the *snake* `is_error`, and that is also captured rather than chosen: the
handler-side shape in `handler-calls.jsonl` is `{"content": [...], "is_error": true}` and the SDK is
what turns it into the wire's `isError`. The two spellings in this module differ because the two
captures differ, and that sentence is in the module docstring so the next reader does not "fix" one.

## T11-4 · §T7-3's blindness, met head-on in this task's own DP4 check — and a literal-only resolver was measured missing the shipped fixture · owner: T11, applied locally, shared helper untouched

**Symptom.** `test_export_imports_no_vendor_package` asserts this module imports no vendor package.
Written with an import-node walk plus literal-argument call resolution — i.e. §T7-3's fix, minus the
constant lookup — it **passed on `export.py` and could not see the shipped dynamic fixture**:

```
E  AssertionError: ('toolsurface_imports_the_vendor_sdk_dynamically.py',
                    {'__future__', 'importlib', 'mcp'})
E  Extra items in the left set: 'claude_agent_sdk'
```

`__import__("mcp")` resolves from its literal; `importlib.import_module(VENDOR)` does not, because the
fixture names the package through a module-level constant — which is how the spelling is idiomatically
written, and exactly what T7 said its widened helper resolves.

**What was tried.** The local scanner now resolves module-level string constants as well as literals,
and it is **proved to bite before it is used to report an absence**: it is driven over both inert
fixtures (`toolsurface_imports_the_vendor_sdk.py`, `toolsurface_imports_the_vendor_sdk_dynamically.py`)
with the expected roots written out, and only then over `export.py`. The fixtures are **read as text
and parsed as an AST, never imported** (CLAUDE.md: a planted violation is a fixture nothing imports),
and **nothing was planted into live source in any tree** — the vendor import that would prove the rule
is 208 MB of code that *runs*, and the existing frozen fixtures make planting unnecessary.

`tests/boundaries/_imports.py` was **not** touched: §T7-3's `module_imports` → `all_imports` widening
is still owned by whoever next works on a quiescent tree, and four builders were live during this task.

**What it blocks.** Nothing. The local check duplicates a claim the boundary rule already makes over
the whole tree; it exists so the claim fails *where a reader of `export.py` looks for it*.

## T11-8 · The scratchpad this session was told was isolated is **shared between concurrent builders**, and a sibling overwrote this task's mutation script mid-task · owner: process hazard, recorded, worked around

**Symptom.** The environment preamble describes
`/tmp/claude-0/-root-Shepherd/<id>/scratchpad` as *"session-specific, isolated"*. It is not isolated
between the concurrent M4 builders. This task wrote `scratchpad/mutate.py` (its mutation driver) and
`scratchpad/final.txt` (a sweep log). Re-running `mutate.py` minutes later printed **another task's
mutation table** — twelve rows about a system prompt, `test_the_prompt_names_no_vendor`, paraphrase
survivors — i.e. T19's script under T11's filename. `final.txt` was rewritten under this task too.

**What was tried.** Every T11 scratch file was renamed with a task prefix (`t11_mutate.py`,
`t11_export.orig.py`) and the mutation table above was **re-run from scratch** under those names, with
a byte-comparison of the restored source afterwards. The earlier run's results were identical, so
nothing in this file rests on the clobbered run.

**Why it is worth a ledger entry.** It is the same shape as this directory's own reason for existing:
*"append to this file" is an instruction, not a concurrency protocol*, and two tasks' entries were
destroyed by it. A generic filename in a shared directory is that hazard again, one layer down — and
here the shared object is a **script that rewrites files under `src/` and restores them from a
backup**. The failure mode that did not happen, but could have, is a sibling's restore step writing
its backup over a file this task had mutated.

**Already ruled on, independently, while this task was running.** `router-decisions.md` §RD-T17-11
records the same collision between T3 and T17 and sets the rule: scratch work goes in
`scratchpad/m4-<task>/` and nowhere else. This entry is the **third** instance (T3↔T17, and here
T19↔T11) and is kept because it is the first one where the clobbered object was a script that
rewrites files under `src/`. T11 wrote nothing into the repo's `scratchpad/`; its scratch files are
task-prefixed (`t11_mutate.py`, `t11_export.orig.py`) in the session temp directory.

**What it blocks.** Nothing. **Owner: every M4 builder while the milestone runs in parallel** —
RD-T17-11's directory rule, and task-prefix the filenames inside it too.
