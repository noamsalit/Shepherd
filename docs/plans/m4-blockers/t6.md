## T6-1 · M1's `test_no_authorize_call_exists_yet` is **retired**, and this is the reason · RD-T4-4, **applied**

**What it was guarding.** M1's plan: *"M1 has no gate; a test asserts the symbol is absent, so M4's
addition is visible in the diff."* It walked every identifier under `toolsurface/` and asserted
`"authorize" not in names` and `"audit_log" not in names`.

**Why it is gone rather than edited.** The event it watches for **has happened**: T6 put
`authorize()` and the audit write inside `invoke()`. Task 6's *Files/Surfaces* says *"existing M1
tests must still pass unchanged"*; RD-T4-4 already recorded that the sentence and the tripwire cannot
both be honoured, and the sentence is the one that is wrong. T4 did not dodge it — it named its
closure `_authorize` and proved the tripwire was **still armed** with MUT-12 rather than leaving the
dodge unverified. T6 finishes that: deleted, with this reason, in place (a retirement note sits where
the test was, the way `export.py` kept `tools_list_payload`'s).

**And a measured detail that makes the retirement the *only* honest option.** The tripwire would
have **stayed green** after T6. `invoke()` holds an `Authorizer` and calls it through a local named
`authorizer`; the audit goes through `AuditRecord`/`AuditSink`/`_audit`. None of those identifiers is
`authorize` or `audit_log`. So narrowing it to "a spelling that still passes" was available and is
worse than deletion: **a tripwire that is green after the event it watches for reads as evidence
that the event did not happen.** That is this repo's dominant defect class, committed inside the
check written to prevent it.

**What guards the property now** — positively, which is a stronger statement than an absent symbol:

| was | is |
|---|---|
| `authorize` appears nowhere under `toolsurface/` | `test_no_handler_runs_before_the_gate_answers` — the gate is **consulted inside `invoke()`**, and consulted before any handler (MUT-1 red) |
| — | `test_invoke_fails_closed_without_a_gate` — what happens when it is absent (MUT-2, MUT-3, MUT-4 red) |
| `audit_log` appears nowhere under `toolsurface/` | `test_every_blast_class_audits_exactly_once` — the audit write exists and happens exactly once per decided call (MUT-5, MUT-6, MUT-18 red) |

The gate is no longer *visible* in the diff. It is *required* by the suite.

## T6-3 · `autonomy_level` has **no source** at `invoke()`, and the record says so rather than guessing · owner: **router**, one field on `AuthzOutcome`

ADR-M4-1's record carries `autonomy_level: int`. Nothing hands `invoke()` one:

* `AuthzOutcome` carries `allowed`, `approved_by`, `approval_id`, `reason` — **not the level the
  gate read**, though `build_authorizer` calls `level()` and knows it;
* `install_chokepoint(authorizer, sink)` is pinned at two parameters by the plan's *Produces*;
* `invoke()` has no route to a `Store`, and `toolsurface/client.py`'s `autonomy_level()` is the
  master's client, injected by a composition root that does not exist yet.

Writing `2` — the default — would be **K23's overclaim in the artefact the next incident is
reconstructed from**: the record would say *this ran at level 2* when the process never asked. So
`UNREPORTED_AUTONOMY_LEVEL = 0` is written, and `0` is asserted **outside** `AutonomyLevel`
enumerated at test time (`{2, 3}`), so a `jq` reader can tell *unreported* from *reported*. MUT-16
sets it to `2` and is red.

**The fix is one field** — `autonomy_level: int` on `AuthzOutcome` in `types.py` (T3's file, stdlib
only, and the authorizer already has the value). Not applied here: `types.py` is not T6's, and
T6 inventing a field on a pinned dataclass is the shape this milestone keeps refusing. Owner:
router; it belongs in the same pass as RD-T4-3 and §T6-4.

## T6-4 · `actor_kind_of` now exists twice, visibly rather than possibly · owner: **router**, same pass as RD-T4-3

`registry.py` cannot import `audit.py`: `audit.py` imports `shepherd.logs.jsonl`, `cli/` imports
`registry`, and the shipped DP3 rule **only checks direct importers** — so the import would pass the
rule while defeating it, dragging `shepherd.logs` into `shepherd status`. This is `types.py`'s own
docstring, arriving from a third direction (T4's `SECRET_KEY_MARKERS`, T5's, now this).

So `registry._actor_kind_of` is `audit.actor_kind_of` said a second time, and the drift is made
**visible instead of possible**: `test_the_actor_kind_derivation_has_no_second_opinion` compares the
two over every `Audience` enumerated at test time **and** over an explicit `actor_kind`, and MUT-15
(derive unconditionally, DP2's defect) is red. The real fix is one definition in `types.py` — the
same one-line repair RD-T4-3 already owes. **Three copies of one rule is a pattern, not an accident**
(RD-T5-5).

## T6-5 · P-M4-2, read as the **pair**, written identically in all three places · **decided**

P-M4-2 was ambiguous between *"every tool in the registry"* and *"one per blast class"*. T6 takes the
**pair**, which is the reading the plan's revision 2 already argued for and the only implementable
one: driving every shipped tool for real means `install_hooks` writes a settings file Claude Code
owns.

* `test_every_blast_class_audits_exactly_once` registers **one synthetic tool per `BlastClass`,
  enumerated from the enum at test time** (`AUDITED_CLASSES = set(BlastClass)`), invokes each, and
  asserts one record per call naming that tool. No literal count, no literal class list.
* `test_the_shipped_blast_classes_are_covered` discovers the classes the **shipped** tool modules
  declare — by AST over `blast_class=BlastClass.X` keywords under `toolsurface/`, never a list — and
  asserts `shipped <= AUDITED_CLASSES`.

**The subset check is not allowed to be vacuous**, so it asserts the scan found something *before* it
asserts anything about what it found, and asserts `LOCAL_DESTRUCTIVE` is among them (D38.1's
installer trio). MUT-14 points the scan one letter wrong and it is red at *"the scan found no shipped
blast class at all — it is pointing at nothing"*. That is the plan's own rule about a different scan
— *a scan of nothing finds nothing* — applied to this one.

## T6-6 · What `install_chokepoint` makes unrepresentable, and what it does **not**

**Unrepresentable, and proved three ways.** *A gate with no audit log.*

1. The slot is **one value**, `_CHOKEPOINT: tuple[Authorizer, AuditSink] | None`, and
   `test_the_chokepoint_cannot_be_half_installed` **discovers it by property** — the module global
   whose annotation names both `Authorizer` and `AuditSink` — rather than by spelling.
2. Every function that writes that slot either clears it to `None` or takes parameters annotated with
   both. MUT-10 adds `install_gate(authorizer)` — a second writer that conjures its own sink — and it
   is red at *"install_gate() writes _CHOKEPOINT without being handed both halves"*.
3. `install_chokepoint` has **no defaulted parameter**, so neither half can be omitted at the call
   site. MUT-9 defaults both and is red. (T5 gave `build_audit_sink` the same property one layer
   down, deliberately: §T5-3 named this half as T6's.)

**And clause 2 is no longer self-sealing.** With no chokepoint, `invoke()` **refuses** every class
outside `GATE_FREE_CLASSES` — so *no decision, no record* can no longer be produced by a destructive
call, only by a call that was refused before there was anything to authorise. MUT-2 restores
revision 1's permissive absent-state and is red; MUT-7 moves the audit above the gate and is red at
*"an undecided call was audited: ['needs_an_id']"*.

**Not closed, and named rather than hidden.**

* **G-M4-17 stands.** A `local_read` call in a non-composing process is still unaudited. That is the
  price of `GATE_FREE_CLASSES` and the reason it has exactly one member; MUT-4 empties it and is red
  at *"local_read must still run: cli/ depends on it"*, which is the `cli/`-and-Gate-A side of the
  same trade.
* **P-M4-4 is still T25's.** Every test here injects its own sink, so what is proved is that
  `invoke()` writes **one record per decided call** — not that the shipped composition installs a
  real log. `compose_tool_surface` composes no chokepoint on this tree; T5 said the same thing from
  its side (§T5-2) and T6 asserts nothing that could be mistaken for it.
* **`install_chokepoint` has no caller in `src/`.** It belongs on the router's *"no caller"* register
  until T25 wires it: two lines in `compose.py`. Unlike the other rows, the mechanism is **not**
  dormant — `invoke()` reads the slot on every call, and the absent state is now a *refusal*, so the
  un-wired state is loud rather than silent.

## T6-7 · The mutation ledger — 20 applied, 20 red, and the one the **harness** swallowed

**Technique, per RD-T19-7.** Every mutation is applied to `scratchpad/m4-t6/shadow/` (`src/`,
`tests/`, `pyproject.toml` copied; pytest run with `cwd=` the shadow). **No file in the live tree was
mutated, not once, not briefly.** Every mutation is pure data or control flow — a branch order, a
frozenset member, a dict key, a signature default — so nothing escapes the process (CLAUDE.md,
2026-09-17). Driver: `scratchpad/m4-t6/t6_mutate.py` (the shadow tree is rebuilt with
`cp -r src tests pyproject.toml scratchpad/m4-t6/shadow/` and deleted afterwards, so a second copy of
`src/` is not left lying in the repo); the restore is asserted, not assumed; every
wait in the gate tests is bounded, so a mutant that hangs is a failure and not a hang.

|---|---|---|---|
| MUT-1 | the gate consulted **after** the handler has run | RED | `AssertionError: a handler ran before the gate answered` |

| MUT-20 | the chokepoint removed from an M1 test's `local_write` fixture | RED | `assert <Failure.UNAVAILABLE> is <Failure.FAILED>` |

**MUT-16 reported SURVIVED on the first pass, and it was the harness, not the test.** The mutation
`0` → `2` is the only one in the ledger that **preserves the file's size**, and it landed inside the
same mtime second as the restore before it. CPython's `.pyc` validity check is `(mtime, size)`, so
the interpreter re-imported the **unmutated** bytecode and the test passed on code that was no longer
on disk. Applied on its own it is red at `assert 2 not in {2, 3}`.

The lesson is the one this repo keeps relearning in a new costume: *when a result surprises you,
suspect the observation method before the system.* A mutation driver that does not clear
`__pycache__` **cannot report a size-preserving mutation as red, ever** — and a survivor in a ledger
is read as a hole in the tests. The driver now clears bytecode before every run, and the reason is in
its docstring so the next builder does not have to rediscover it. Worth stating plainly: had MUT-16
been the only mutation of `UNREPORTED_AUTONOMY_LEVEL`, this file would have recorded a false hole.

   cap, reported twice; `MASTER_TOOL_UNEXPECTED is incremented at ['master/sdk_master.py'] — remove

   rule, obeyed from the second producer.

   T7's content out of the assembled ledger.
