## T26-2 · P-M4-18 and K21: the net's derived set, and the hole in the obvious form

`test_the_live_net_covers_the_m4_modules` asserts that the gate's **derived target set contains**
`tests/e2e/test_live_master.py`, `tests/e2e/test_live_master_isolation.py` and
`tests/e2e/conftest.py`. The existing gate proves the derivation type-checks whatever it found; it
says nothing about **what** it found, and *"a net that silently stopped covering them is the same
defect one layer out"*.

Two things are worth recording about how it is written.

**The expectation is typed out, not derived.** The derivation is the thing under test, so an
expectation derived the same way would agree with it by construction and could never disagree —
the tautology this repo names by name.

**The obvious form has a hole, and it is closed.** `M4_LIVE_MODULES <= targets` is vacuously true
when `M4_LIVE_MODULES` is empty, so the check asserts its **own expectation** is non-empty before it
asserts containment — and **D3** is the mutation that proves that line is load-bearing: emptying the
frozenset is red. Without it, deleting three lines would have turned the K21 check into a check of
nothing while leaving it green, which is precisely the failure mode K21 exists to name.

`live_lane_targets()` was extracted so the two checks read **one** definition of the derived set.
The alternative — a second copy of the `conftest.py`-sibling rule inside the new check — is
RD-T5-5's shape: *a rule copied into a second file is a rule that can be widened in one place and
keep reporting the old answer from the other.* **D1** (the sibling rule dropped) is red on the new
check, and **D4** (node ids resolved to their directory) is red on **both** — which is the row that
says the two really do share the definition.

## T26-4 · The teardown ledger, and why it is the socket set rather than `tmux … ls`

**The pid ledger has two halves, and both are arrival-first.**

*Ours.* The engine's pid is read off the vendor's transport while the turn runs, asserted **alive at
the instant it is recorded** — `pid_cmdline(pid)` must be non-empty — and only then asserted gone.
Recognition is by `argv[0]`'s **basename**, never by spelling: the SDK spawns its own bundled
`…/claude_agent_sdk/_bundled/claude` rather than `PATH`'s, so a rule keyed on the string `"claude"`
would see the operator's Remote Control sessions and miss the one this lane started — an emptiness
that means nothing. Measured: pids `488636` and `488674`, both `/root/Shepherd/.venv/lib/python3.12/
site-packages/claude_agent_sdk/_bundled/claude`, **survivors: `[]`**.

*The host's.* Every `claude` on this machine before and after, as a **set**: `[6648, 6684]` before,
`[6648, 6684]` after — the operator's own two Remote Control sessions, which predate this task. The
assertion is *"the after-set contains nothing the before-set did not"*, never a count: an assertion
on how many there are fails whenever the user opens a terminal (F10, and CLAUDE.md's rule that the
names are not the invariant).

**The tmux ledger is the socket set, read off `/tmp/tmux-<uid>/`, and that is a deliberate choice.**
`tmux -L … ls` contacts a server and builds an argv; a check that the lane left no tmux behind must
not be the thing that starts one, and the user's socket cannot be reached through the shipped exec
site at all (`permitted_sockets` refuses `FORBIDDEN_SOCKET` at construction). Reading the directory
names nothing and contacts nothing. Measured, before and after this task's live lane:

```text
shepherd  shepherd-m3-live  shepherd-m3-rename
```

Identical. **No `shepherd-m4-*` socket was ever created** — `tmux -L shepherd-m4-t26 ls` answers
`error connecting to /tmp/tmux-0/shepherd-m4-t26 (No such file or directory)`, and both
`shepherd-m3-*` sockets answer `no server running on …`.

**An emptiness needs a reader that can see something, so the reader has a positive control.**
`test_the_socket_ledger_can_see_a_socket` binds a real `AF_UNIX` socket inside `tmp_path` and asserts
the reader reports it, and asserts a *regular file* in the same directory is **not** reported. **L6**
— the reader answers `frozenset()` unconditionally — is red on it. Without that row,
`sockets_after - sockets_before == set()` would be M3's `count == 1` again: a pass that cannot fail.

## T26-5 · What was **false** of this task's own first draft, measured and corrected

**The module docstring said *"no tmux at all"*. That is false of this tree.**
`compose_tool_surface`'s startup reconcile calls `reconcile_owned_panes`, which calls
`runner.list_owned_panes()`, which execs `tmux -L <socket> list-sessions`. So the composition *does*
build a tmux argv, at compose time, before any of this task's assertions run.

It was corrected rather than left, and the correction is the reason the run writes
`app_state["runner_socket"] = "shepherd-m4-t26"` before composing: `make_run_argv(permitted_sockets(
"shepherd-m4-t26"), …)` is then an exec site that **refuses every other socket by construction**,
never the user's and never the product's `shepherd-runner`, which a test must not share.
`list-sessions` contacts a server and never starts one, which is why the socket set is unchanged. The
check asserts the socket back through the shipped resolver (`compose.runner_socket(store)`) rather
than trusting the write.

**Recorded because the general shape is the reusable part:** *"this lane starts no X"* is a claim
about a whole composition, and a composition is exactly the thing that does more than the test author
had in mind. The belt (a throwaway socket the exec site is constructed around) is worth more than the
sentence.

## T26-6 · The finding that matters most: **the release key has three producers**

This is the one thing in this task that changes what a reader should believe about the tree.

RD-T4-2 is the milestone's sharpest decision — *"a wrong key is worse than an absent one, because it
fails silently"* — and T25 §T25-3 closed it. So the obvious live mutation is *key the withdrawal on a
plausible-looking literal and watch the worker ride its deadline*. **It survives.** Three times.

| row | site keyed on a plausible ULID that is nobody's turn | result |
|---|---|---|
| **L3** | `TurnDriver.interrupt_master` → `self._withdraw(PLAUSIBLE)` | **survived** |
| **L3b** | `AgentSDKMaster.interrupt` → `self._withdraw_turn_approvals(PLAUSIBLE)` | **survived** |
| **L3c** | **both** of the above at once | **survived** |
| **L3d** | both, **plus** `AgentSDKMaster.close` → `self._withdraw_turn_approvals(PLAUSIBLE)` | **red** |

There are **three** withdrawal sites on the interrupt path, and each is independently sufficient:

1. `TurnDriver.interrupt_master()` withdraws by the turn's id before it touches the runtime
   (ADR-M4-3);
2. `AgentSDKMaster.interrupt()` withdraws again, by `self._turn_id()`, before it schedules the
   vendor's interrupt;
3. `AgentSDKMaster.close()` withdraws a third time — run from `TurnDriver._run_turn`'s `finally` on
   **every** turn, and its own docstring says the repeat is deliberate (*"a second one frees nothing
   and costs nothing, while skipping it on a re-entrant shutdown would leave a worker blocked"*).

**This is not a defect and it is not a test gap. It is redundancy, and the honest consequence is that
no single-site mutation can be a red.** L3, L3b and L3c are recorded as survivors *with that reason*
rather than banked as passes or quietly dropped, because a survivor is information: what it says is
that a reader who repairs one of these three sites and re-runs the live lane will see green, and will
be wrong about why.

**Two consequences worth carrying forward.**

* **For the milestone verifier.** "The release is keyed on the live turn" is proved here (L3d is
  red), but it is proved *of the three sites together*. Any future check written to bite on one of
  them — a mutation ledger row, a review comment, an AST rule — is checking a spelling.
* **For whoever owns RD-T5-5's single-definition-site pass.** This is a fourth instance of its
  shape, in a new place: not *a rule with several implementations* but **a capability with several
  producers**. It is defensible here (P2 measured that our own compare-and-set is the *only* release
  path, so belt and braces is proportionate) and it is not something to collapse under deadline. It
  should be written down beside the others rather than re-discovered by the next person who plants a
  mutation and watches it survive.

## T26-7 · `plane.build_master` passes no `settings`, so the live belt is the lane's

Recorded as an observation, not a defect. `daemons/plane.py`'s constructor call is

```python
AgentSDKMaster(caller_id=…, turn_id=…, bump=…, withdraw_turn_approvals=…, model=_model(store))
```

— no `settings`, which is exactly D42's block (`sdk_master.build_options`' own docstring:
*"`settings` is `None` in D42's block"*). In production that is right: the isolation lever is
`setting_sources=[]`, P4 measured that it excludes the operator's user scope, and the shipped
`--setting-sources=` above is that lever in the argv.

What follows is a **live-lane obligation rather than a product one**: a test that starts a real
engine straight off `plane.build_master` would let that engine read the operator's own
`~/.claude/settings.json`. T21's and T22's live runs both passed `settings=` for the same reason and
the probe harness recommends the two levers be kept separate. So this task substitutes the
constructor — nothing else — and says so in `SUBSTITUTIONS`. **Anyone writing the next live check
against the plane inherits this obligation and there is nothing in the tree that reminds them of
it.**
