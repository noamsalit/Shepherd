## T20-0 · `tools_list_payload` is **not** consumed — RD-T11-1's decision is owed now · owner: router

**The answer RD-T11-1 waits on: no.** `build_sdk_server` consumes `ExportedTool` and hands
`(name, description, input_schema)` to `@tool`; `create_sdk_mcp_server` builds the `tools/list`
entry itself, in its own `Tool` model, with its own camel alias. There is no point in this module at
which a pre-built wire payload could be passed in — the SDK does not accept one — and T11 said so
when it shipped the function (§T11-1: *"the master binding does not consume a `tools/list` payload
either"*). Measured rather than reasoned: `grep -rn "tools_list_payload" src/ tests/` finds it in
`toolsurface/export.py` and in T11's own test and nowhere else, with this task's files on disk.

The shape it encodes **is** re-asserted here, though not through it:
`test_the_schema_and_description_reach_the_wire_unchanged` compares the vendor's own `tools/list`
answer, dumped by alias, to `{"name", "description", "inputSchema"}` written out as a literal — the
same three keys and the same camel spelling T11 captured. So retiring the function in place loses no
evidence.

## T20-1 · The pinned signature cannot carry the turn id, and a plausible id would fail silently · owner: T20 applied a seam; **two lines are still owed**, owner T21/T25/T27

**Symptom.** §T4-2 names it exactly: `ApprovalStore.create()` reads an approval's `turn_id` from
`ctx.correlation_id`, `withdraw_all(turn_id)` matches on it, and the plan's
`build_sdk_server(tools, caller_id)` has **no** parameter that could carry a turn. P2 measured that
no cancellation reaches a running handler, so the withdrawal is the *only* thing that can release a
worker blocked in `await_decision` — a key that matches nothing turns the one working release
mechanism into decoration while every test stays green.

**What shipped.** `build_sdk_server` takes a required keyword-only `turn_id: Callable[[], str]` and
the handler calls it **per call**, passing the result as `correlation_id`. A supplier rather than a
string because the runtime outlives the turn: T27 mints a fresh ULID per turn
(`master_turn.py:182`) and `build_master()` takes no arguments, so a turn id captured when the
server is built would key every later approval to a turn that has already ended. Both halves are
asserted:

* `test_a_withdrawal_releases_the_blocked_call_before_its_deadline` drives the **real**
  `ApprovalStore` with an injected clock that never advances: a card is raised inside the substituted
  `call`, the worker blocks in `await_decision`, `withdraw_all(TURN)` resolves exactly one approval,
  and the handler comes back with `withdrawn` while `deadline_at` is still ten minutes in the future.
  M5 (a plausible-looking `"correlation-1"`) is the mutation that proves it.
* `test_each_call_carries_the_turn_it_is_running_inside` drives two calls against a supplier that
  answers two different ids. M6 (captured at build time) is the mutation that proves it.

**What is still owed, named precisely.** Nothing in the tree calls `build_sdk_server` yet, so the
supplier has no producer. The closing edit is **in T21 and T25, not here**: `plane.build_master`
(T25) builds the master and is where `bump` comes from, and `AgentSDKMaster` (T21) is what holds the
options block — one of them must hand this module a callable that answers the **current** turn's id,
which today only `MasterTurnDriver` knows (`master_turn.py:182`, `:214`). Either the driver's
`build_master: Callable[[], MasterRuntime]` grows a `turn_id` argument (T27's file), or the driver
exposes the live turn id and the plane closes over it (no signature change). **T20 cannot close it
and did not invent a value that merely looks plausible** — §T4-2's own instruction.

## T20-2 · `bump` is the second injected callable, for the same reason · owner: T20, recorded

`MASTER_TOOL_RESULT_ORPHANED` is raised in `master/`, which D19 forbids from importing a store, so
it arrives as a required keyword-only `bump: Callable[[AnomalyKind], None]` — injection is not an
import, and the K24 resolver classifies the site as **reachable** precisely because the member is
handed to a bump-shaped call in a module that imports no store
(`tests/test_core_master.py::increment_sites`).

Neither `turn_id` nor `bump` is defaulted. A default for either is the failure this milestone has
already paid for twice: a counter nobody increments (K24/K9) and a release key that matches nothing
(§T4-2). A missing argument is a `TypeError` at composition; a defaulted one is a silent zero.

Both are **deviations from the plan's pinned `Produces` block**
(`build_sdk_server(tools: tuple[ExportedTool, ...], caller_id: str) -> McpSdkServerConfig`), recorded
here rather than absorbed. `MASTER_TOOL_CAPACITY` and `MASTER_TOOL_LIMITER` are also beyond the block
and are the plan's own names from ADR-M4-3 and RD12.

## T20-5 · The test seam is the vendor's own server, and what that avoids · owner: T20, recorded

Every translation assertion drives the real `mcp.server.Server` that `create_sdk_mcp_server`
returns — `get_request_handler("tools/list")` and `get_request_handler("tools/call")`, i.e. the code
path the CLI drives — rather than reading back the `SdkMcpTool` objects this module built. Three
consequences worth writing down:

* **It is not a tautology.** A projection test that builds its expected value out of the object under
  test cannot disagree with it (T27's survivor). The expected schemas, descriptions and wire keys are
  **literals** in the test; the actual values come from the vendor's own `Tool.model_dump(by_alias=…)`.
* **The D53 branch is exercised in both directions.** A schema with a string `type` and `properties`
  is asserted to arrive unchanged, and a `{param: python_type}` schema is asserted to arrive
  **mangled** — `{"type": "object", "properties": {"project_id": {"type": "string"}}, "required":
  ["project_id"]}` — which is what makes the first assertion a measurement of the branch rather than
  a coincidence. Re-measured against the installed 0.2.153, as the task requires.
* **It is the only public way in.** mcp 2.2.0 keeps `_request_handlers` private but exposes
  `get_request_handler(method)`; its `HandlerEntry.handler` is what the test awaits. Recorded because
  it is version-shaped: on mcp 1.x the same server is built through decorators and this seam moves.

`call` is the single substitution, patched at the module global the handler resolves at call time.
Everything else in the path — `@tool`, `create_sdk_mcp_server`, the SDK's `jsonschema` validation,
its content conversion — is the shipped vendor code.

## T20-6 · P2's answer, recorded as the confirmation the task asks for · owner: T20

The exit criteria ask for P2's answer in Progress notes; the plan is not this task's to edit, so it
is here. **P2 is a confirmation and it confirms the stronger reading:** cancellation does *not* reach
a running in-process handler — not deferred, never delivered, no `control_cancel_request`, and the
worker thread ran all twenty of its seconds
(`docs/probes/2026-09-17-m4-sdk/p2-interrupt-20260917T215207Z/handler-calls.jsonl`). **Nothing in
this module's design changes**, and that is the sentence the criterion asks for: the release path is
our own store's compare-and-set, driven from `AgentSDKMaster.interrupt()`/`.close()`, and this file
contains no withdrawal logic at all.

`abandon_on_cancel=True` is therefore **not** the release mechanism and is not documented as one. It
exists so that a cancellation which *does* arrive — P2 saw one variant deliver `CancelledError` at
client teardown — cannot pin the loop behind a worker that is still blocked. When it fires, the
worker keeps running and its result is discarded, which is why `MASTER_TOOL_RESULT_ORPHANED` is
counted on exactly that path.

## T20-10 · `CLAUDE.md`'s new mutation rule 4 applied retroactively to this task's one survivor · owner: T20, re-measured

`CLAUDE.md` gained a rule after this task's table was taken: **clear `__pycache__` before every
mutation run**, because CPython decides a `.pyc` is fresh from *(source mtime in whole seconds,
source size)*, so a **size-preserving** edit landing inside the same second re-imports the
**unmutated** bytecode and is recorded as a **false survivor** — a hole written down as a proof that
there isn't one. T20's driver did not clear the cache, and T20 recorded one survivor, so the row was
re-measured rather than left standing on the old run.

**The exposure is survivors only, and T20 has one.** A recorded red proves the mutation took effect;
the ten reds in §T20-7 are unaffected by the rule and were not re-run. BAD-MUT was, with the cache
cleared first (`scratchpad/m4-t20/t20_recheck_badmut.py`):

```text
size before: 8314 size after: 8324 size-preserving: False
BAD-MUT with a cleared cache: exit 0 | 10 passed in 1.36s
SOURCE IDENTICAL TO PRE-MUTATION: True
LIVE TREE UNTOUCHED: True
```

**It is a true survivor, on two independent grounds.** The re-run with a cleared cache passes on its
own terms; and the edit is **not size-preserving** (8314 → 8324 bytes), which is the half of CPython's
freshness check that the hazard needs in order to bite. The row stands as written: mount order is
deliberately not asserted, the SDK dispatches by name, and a suite that went red there would be
over-fitted to an ordering nothing depends on.

**Checked while here, so the next reader does not:** none of M1–M10 is size-preserving either, so
the rule could not have produced a false *red* or masked one of them — and a red would not have been
in question anyway. The shadow tree's caches were removed after the re-check.
