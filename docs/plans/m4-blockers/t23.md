## T23-3 · `report_blocked` and `request_help` **refuse**, because `invoke()` discards the caller · owner: T23, applied

G-M4-15 says the two tools are registered and reachable by nothing. It does not say what their
handlers do, and the three available answers are not equal:

1. **a `session_id` argument** — this is precisely the *unscoped cross-project write API* the Track C
   cut refused by name (`registry.py`'s `_run` is `data = tool.handler(args)`; six `SESSION` tools
   taking arbitrary session ids is what got the binding cut). Rejected.
2. **a silent success returning `{}`** — a stub with a passing test, which M4's acceptance would count
   as evidence. This is the `to_stdio_mcp_server` / RFC-6455-parser shape. Rejected.
3. **a typed refusal naming the missing fact.** Shipped.

`invoke()` checks the caller's audience and then **discards the caller**, so a session-audience handler
structurally cannot know which session is reporting. The repair the cut names — `ctx` bound into the
call plus an enumerated per-tool scope property — is M4.5's, not M4's. So `_no_caller` raises
`ToolArgumentRefused` with `NO_CALLER_TEXT`, which reaches the caller as `Failure.REFUSED` with a
message that names the gap (G-M4-15, G-M4-18). `test_an_unreachable_session_tool_cannot_act_on_a_
session_it_cannot_name` drives both tools; **MUT-9** replaces the refusal with `lambda args: {}` and is
red.

**A second §13 decision in the same family:** `project_approval` carries `summary` (which `describe()`
has already redacted) and **not** `approval.args`. The raw mapping is not redacted, and a sidebar
rendering it would put an unredacted token on the page beside a button. Asserted as a **set equality
over the projection's keys** plus a literal-secret search; **MUT-14** adds `args` back and is red.

## T23-4 · The byte budget is a **measurement**, taken by this task because step 0b row 9 was never taken · owner: T23, applied; the provenance limitation is **recorded, not closed**

**The debt.** Step 0b row 9 — *build a 200-session fixture fleet against the current tree and record
`fleet_summary` and `fleet_tree` byte counts* — is marked `open` / **BLOCKER-T1-6**. T1 refused to
invent it (building a fixture fleet is code, outside a probe's scope), which was right.

**The measurement.** Taken by `scratchpad/m4-t23/measure_fleet_bytes.py`, which is **separate from the
check that asserts it** — a budget computed by the test it constrains is a tautology, not a budget.

```text
$ .venv/bin/python scratchpad/m4-t23/measure_fleet_bytes.py
fleet_summary: 12927 bytes at 200 sessions
fleet_tree: 139323 bytes at 200 sessions
```

Run twice, byte-identical both times: every fixture string is fixed and ULIDs are 26 characters
whatever the run. The fleet is 200 sessions over 8 workspaces with a **quarter of them `needs_you`** —
that list is the term G-M4-8 names as unbounded, and a fleet with none of them would measure the
projection with its growth term at zero. `json.dumps(..., separators=(",", ":"))`, because the number
is a proxy for what the master's context pays and a pretty-printer's indentation is not a fact about
the projection.

**G-M4-8's finding arrives on schedule, and it is a blocker entry rather than a budget edit.** §11's
context strategy promises *"~40 lines regardless of fleet size"*. `fleet_tree` is **139 KB** at 200
sessions — on the order of 35 000 tokens for one call — and `fleet_summary` is 12.9 KB, of which the
`needs_you` list is the part that grows. The plan's own disposition stands: *the lever is the audience
set, and that change is M5's with the measurement in hand.* Nothing was changed here; `fleet_summary`
and `fleet_tree` are M1's code and no M4 task lists `tools_m1.py` in its Files/Surfaces.

**What this measurement cannot claim, said plainly.** The plan wanted the number taken *before any M4
code*. It is taken after. Everything in this repo is untracked on one baseline commit, so there is **no
way to check out the pre-M4 tree and re-measure** — the same limitation clause 6 records for Gate A's
manifest ordering. What is checkable and is checked: the two projections and the three functions under
them (`project_session`, `project_fleet_row`, `project_needs_you`) live in `tools_m1.py`, which no M4
task touched. So the number is a **no-regression baseline against today's tree**, and it is the
strongest honest statement available, not the one the plan asked for.

**The check is not vacuous, and that is proved rather than argued.** A `<=` assertion over an empty
fleet passes while proving nothing, so the arrivals go first — `session_count == 200`, and
`needs_you` non-empty. **MUT-21** builds a 0-session fleet (red at `assert 0 == 200`), **MUT-22**
removes every `needs_you` row (red at the named assertion), and **MUT-23** grows `project_session` by
one field (red at `fleet_tree is 152323 bytes … over the measured baseline 139323`). The budget bites,
and so do both arrivals above it.

### The survivor worth reading: **MUT-15 was the tautology, in T23's own file**

`test_the_autonomy_level_defaults_to_a_real_level_on_an_empty_store` asserted

```python
assert payload("get_autonomy_level", {})["level"] == int(DEFAULT_AUTONOMY_LEVEL)
```

— the expected value read back off the **module under test**. Flipping the default from the level that
**asks** (2) to the level that **auto-approves** (3) moved both sides and the check stayed green. That
is T27's MUT-11 exactly, arriving in the next task, in the one constant where being wrong means *every
destructive call on a fresh install runs without asking*. Closed by typing the expected values as
literals (`2`, and `previous: 2`) with the reason in the docstring. Two sites had it; both are fixed.

### The second survivor was a **bad mutation**, and is recorded as one

MUT-17 originally widened a type guard to `isinstance(stored, (int, str))`. Behaviourally inert: the
loop below compares `int(level) == stored`, and a `str` never equals an `int`, so the function returned
the default either way. **A mutation that changes no observable behaviour is not a survivor** — it is a
row that proves nothing. Replaced with the mutation that names the real risk: coerce with `int()`
instead of matching a member, so a stored JSON `"3"` becomes auto-approve. The **test** was strengthened
in the same pass — it is now parametrised over `"three"`, `"3"`, `7` and `True` (a `bool` is an `int`
in Python, the sneak `registry._PRIMITIVES` excludes from `number`), with `"3"` as the dangerous case.
Red.

### Two further bad mutations, repaired rather than banked

* **MUT-7** first read `drain(store, now)` — but `tools_master.py` does not import `drain`, so the
  mutant raised `NameError` and went red as a **crash**, not as a moved stamp. A red for the wrong
  reason proves the wrong thing (§T3-4's own point about capturing the failing *line*). The
  replacement imports `drain` locally so the mutant genuinely drains; it is now red at the stamp.
* **MUT-18** first read `if True:`, which made the refusal branch read `answer.turn_id` off a
  `TurnRefused` — an `AttributeError`, again a crash. Replaced with a mutation that mislabels the
  refusal (`"started": True`), red at the dict equality.
* **MUT-16** first read `if False:`, which crashed on `members[level]`. Replaced with one that writes
  the unvalidated integer through, which is what *"any integer is accepted"* actually means.

Four of twenty-three rows had to be repaired to be about what they claimed. That ratio is the argument
for capturing the failing **line** rather than the exit code.
