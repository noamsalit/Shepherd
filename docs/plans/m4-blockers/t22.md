## T22-1 · The allow-list, and the one place the plan's own text is red on arrival

`MASTER_ALLOWED_IMPORTS` is **five module prefixes** plus the standard library, the latter read from
`sys.stdlib_module_names` rather than listed:

```python

           "claude_agent_sdk", "anyio"})
```

**The plan's `Produces` block is what shipped; the plan's *prose* allowed-set is not, and it could
not have been.** Task 22's body writes the allowed set out as *"`shepherd.toolsurface.client`,
`shepherd.core.master`, `shepherd.core.anomalies`, `shepherd.master.*`, `claude_agent_sdk*`,
`anyio*`, and stdlib"* — two named `core` modules rather than the package. Measured on this tree:

```

```

`master/projection.py` imports **`shepherd.core.clock.utc_now`**. A rule written to the plan's
sentence would have been **red on arrival against shipped code** — not a finding about the master, a
finding about the sentence. RD-T20-D19 is the controlling text and it says the package: *"`core/` is
vocabulary and is permitted"*, as an allow-list, never a deny-list. That is what shipped, and it is
also exactly what `tests/toolsurface/test_client.py` already permits, so the two rules agree
(§T22-6).

`shepherd.master` is on the list by T21-9's reasoning, ratified here: D19 bounds what the master
reaches *outside* itself, and a module of the master's own is not the rest of the system.

**Adding an entry is a plan change, not an edit.** `test_the_allow_list_is_asserted_whole` compares
the frozenset against a literal typed out **inside the test**, so the two cannot be changed in one
place — which is the mechanical form of Task 22's own Out-of-Scope Drift line naming this a Decision
pressure.

## T22-4 · `core/` is capability-free — the condition, and where the naive version is wrong

RD-T20-D19 widened D19 *because* `core/` is capability-free, so `test_core_is_capability_free_which_
is_why_the_widening_holds` asserts the condition rather than inheriting it.

**The naive rule — "`core/` imports no capability module" — is red on arrival, and the reason is
worth recording.** `src/shepherd/core/ids.py:9` imports `os`, and uses it once:

```
core/ids.py:76  _last_random = int.from_bytes(os.urandom(10), "big")
```

That is **entropy, not I/O**, and RD-T20-D19's audit was right to pass it. So `os` is not banned
wholesale; the rule is written one level down, at the **identifier**, with
`CORE_PERMITTED_OS_NAMES = {"os", "os.urandom"}`. `os.fork` fails, `os.urandom` passes, and M11 —
adding `os.fork` to the permitted names — is red.

Three classes, because a capability arrives three ways: as a module import (`socket`), as an `os.*`
identifier, and as a **bare-name builtin call** (`open`), which needs no import at all and therefore
leaves no import node anywhere in the file to key on. That last one is `module_imports`' blindness
one node class over, and `identifiers()` does not see it either — it collects dotted names, so
`open(path)` is invisible to it. **Measured**: without the bare-name branch the fixture reports two
of its three classes. That was a real RED during this task, not a hypothetical.

The rule is proved non-vacuous against **shipped** code as well as the fixture:
`core_capability_violations(src/shepherd/store/db.py)` reports `sqlite3`. Nothing was planted into
live source to get that row.
