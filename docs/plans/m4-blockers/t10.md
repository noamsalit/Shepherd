## T10-1 · The `retry_of` writer: a dedicated verb, **not** a defaulted parameter on the session-creating verb · owner: T10, **applied**, with the rejected option recorded

**Decision.** `store/writes.py` gains `link_retry(connection, session_id, retry_of)`, delegated by
`Store.link_retry`. It is the **only** writer of `retry_of` in `src/`, asserted by an AST scan over
the whole package (`tests/store/test_retry_link.py::test_link_retry_is_the_only_writer_of_the_lineage_column`).

**Pressure.** §T8-1 is right and it is the whole reason this task is not ceremonial: nothing wrote
`retry_of`, so D31's cap could pass every test over a hand-planted chain and never fire once in
production. Task 8 recorded the recommendation — *widen the session-creating verb with a defaulted
`retry_of`* — and deliberately did not apply it.

**Options.**

1. **Widen `sessions.py::create_owned_session`** with `retry_of: str | None = None` (Task 8's
   recommendation), plus the matching parameter on `db.py`'s 16-argument delegation and a column in
   `_INSERT`.
2. **A dedicated write-once verb** in `store/writes.py` (applied).

**Why 2, and the reasoning is the transferable part.**

- **A default nobody passes is the defect wearing a parameter.** Under option 1 every existing call
  site of `create_owned_session` keeps compiling and keeps writing `NULL`, and the only test that
  could catch "the retry path forgot to pass `retry_of`" is a test of the retry path — which does not
  exist yet in M4 (see §T10-5). The tree would then hold a *writer that looks present and is not*,
  which is strictly worse than today's honest absence: §T8-1 was found by a `grep` for the column,
  and that `grep` would now return a signature instead of nothing. A dedicated verb has no default to
  forget. Its absence of callers is an absence a `grep` still finds.
- **One writer, one rule set (D37).** `retry_of` is the column D31's cap is computed from. Its single
  writer is now one named verb, in the module whose docstring already makes that claim for
  `apply_stop_verdict` and the nine stop columns — and it is asserted the same way, over `src/`,
  rather than asserted by reading the source.
- **Ownership.** `store/sessions.py` is M3's owned-session module and is not on T10's Files/Surfaces;
  option 1 also changes `db.py` beyond delegation. `store/writes.py` was handed to T10 for exactly
  this purpose.

**The cost, stated rather than left to be found.** The link is written a statement *after* the row
instead of inside its `INSERT`. That is not a race for the cap — `admit` reads the **predecessor's**
chain, which is complete before the new row exists, and both statements run on `controld`'s one
writer thread (ADR-7). It does mean a caller that creates a retry row and then fails before calling
`link_retry` leaves a lineage one short, which under-counts and therefore refuses *later*, never
earlier. The verb is write-once (`AND retry_of IS NULL` in the statement, so a relink is a zero-row
update rather than a silent overwrite) and refuses a self-link, an unknown end, and a link that would
close a loop.

**What it blocks.** Nothing. It unblocks the cap: §T8-1's defect is closed for the column, and the
remaining half — nothing *calls* the writer in production — is §T10-5, which T10 cannot close.

## T10-2 · The cap counts the whole lineage, per §T8-3, read and accepted rather than reinterpreted · owner: T10, **applied**

`reads.retry_chain_depth` counts every link in the `retry_of` lineage, not only the master-spawned
ones. §T8-3 flagged this for T10 to read before using the number, and it is accepted as-is:

- it is **conservative in one direction only** — a lineage a human began and the master continued caps
  one attempt earlier than a master-only count would, so it refuses sooner and never later;
- a master-only count is **a second store verb**, because the lineage does not record who asked for
  each link (`retry_of` is an id, not an audience). That is a change with its own design and its own
  tests, and it is §T10-3 — never a quiet re-reading of the verb T8 shipped.

Asserted at the seam by `test_a_third_master_attempt_is_refused` and its negative control
`test_a_second_master_attempt_is_admitted`, which together pin the boundary exactly: depth 1 admits,
depth 2 refuses.

## T10-3 · A master-only attempt count would be a second verb, and the column to support it does not exist · owner: deferred, **decision recorded, not applied**

**Decision.** Whether D31's *"2 master-initiated attempts per lineage"* should count only the links
the master created.

**Pressure.** The current count (§T10-2) includes human-created links. A human who retried twice by
hand has spent the master's budget on that lineage, and the master's first attempt is refused.

**Options.** (a) leave it — conservative, refuses early, costs the master an attempt in a case that
needs a human in the loop anyway; (b) add `retry_initiated_by` (or fold it into the existing `origin`
of the *retrying* row) and a second read verb `master_retry_chain_depth`, with a migration if it is a
new column; (c) read the retrying row's `origin` while walking — no migration, but it counts the
origin of the session rather than of the *decision to retry*, which are not the same thing when a
human re-runs a master-spawned session.

**Recommendation, not applied.** (a) until a real lineage is refused early in use. If it is ever
built, (b) — because (c) reuses a column for a fact it does not hold, which is the shape D31's own
*"the cap is a property of the lineage, not of the `attempt` column"* warns about.

## T10-4 · The cap ships with no production caller: nothing in M4 spawns a retry · owner: **open**, named for the milestone that builds the retry flow

**Symptom.** `Store.link_retry` and `admit(retry=Retry(...))` exist, are proved, and are called by
nothing in `src/`. Grepped after the change: the only callers are tests.

**Cause, and it is a plan-shape fact rather than an omission.** M4 has no task that retries a stopped
session. T9's `wake.py` drains the wake set into a summary; the master reads it. The verb that would
say *"run that one again"* is a tool on the master's surface, and the M4 plan does not contain it —
Track C's cut removed the session-facing binding, and the master-facing retry tool was never a task.

**What was tried.** The half T10 can close is closed: the cap is proved against chains built by the
**shipped writer** through the public `Store` seam (`a_lineage()` in
`tests/orchestration/test_admission.py` calls `store.link_retry`, never SQL), so the cap has met the
code that will trigger it. What is missing is the call, not the mechanism.

**What it blocks.** D31 end to end. Until a retry flow calls `admit(retry=…)` and then
`store.link_retry(...)`, the cap cannot fire in production *because nothing retries*, which is a
narrower statement than §T8-1's but the same shape. **It closes with two lines in whichever task
builds the retry**: pass `Retry(of=<the stopped session>, initiated_by=Origin.ORCHESTRATOR)` to
`admit`, and call `store.link_retry` after `create_owned_session`. Both are asserted here already.

## T10-5 · `admission.py` is now exactly at T11's 300-line cap, and the obvious escape costs an edit to a suite T10 does not own · owner: recorded, worked around in place

**What was tried, and the measurement is the useful part.** The split was **built and reverted**:
`src/shepherd/orchestration/retry_cap.py`, a pure module returning a reason or `None`, with

That is **§T9-3 exactly**, one task later: any new public callable under `orchestration/` needs an

**What it blocks.** The next builder to touch `admission.py`. It is at 300 of 300; the next addition
