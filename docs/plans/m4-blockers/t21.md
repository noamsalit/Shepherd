## T21-1 · The turn id: T21 holds the seam, and **two lines are still owed** — owner T27, then T25

**T20-1 asked whether T21 could supply it. The answer is no, and here is the precise reason.**

`AgentSDKMaster.__init__` takes `turn_id: Callable[[], str]`, keyword-only and **not defaulted**, and
passes it **unchanged** to `build_sdk_server(..., turn_id=…)`. So the supplier now has a holder, and
the approval key reaches `CallerContext.correlation_id` on every call. What it still has no producer.

The producer cannot be here, for a structural reason and a correctness one:

1. **Structural.** `TurnDriver.__init__` takes `build_master: Callable[[], MasterRuntime]` and calls
   it with no arguments (`orchestration/master_turn.py`, `send_turn`). The driver mints the turn id
   (`new_ulid()`) *before* that call and keeps it on a private `_Turn`; the only public state reader
   it has is `is_running()`. So nothing a composition root can reach today answers *"which turn is
   live"*.
2. **Correctness.** A master that minted its own id would produce a key that matches nothing. The
   driver withdraws by **its** id — `interrupt_master()` calls `self._withdraw(turn.turn_id)` — so
   approvals raised under a master-minted id would never be withdrawn, every blocked worker would
   ride its full 600 s, and every test in the tree would stay green. That is §T4-2's defect
   reproduced at the one place T20 refused to reproduce it. **No value was invented.**

**The two lines, named.** The safe shape is the *argument*, not a reader:

```python
# orchestration/master_turn.py (T27)
build_master: Callable[[str], MasterRuntime]        # was Callable[[], MasterRuntime]
turn.runtime = self._build_master(turn.turn_id)     # was self._build_master()

# daemons/plane.py (T25)
def build_master(turn_id: str) -> MasterRuntime:
    return AgentSDKMaster(..., turn_id=lambda: turn_id, bump=bump_anomaly, ...)
```

A `current_turn_id()` reader on the driver is the alternative and is **worse**: it answers
`str | None`, and every caller then has to invent a string for the `None` case — which is the wrong
key again, arriving through the repair.

## T21-2 · `project_events`, and why the projection is a second module

Two deviations from the plan's pinned `Produces`, both recorded rather than absorbed.

**`project_event(obj) -> MasterEvent | None` became `project_events(obj, *, bump, tool_names) ->
tuple[MasterEvent, ...]`.** `AssistantMessage.content` is a **list** of blocks, so one message can be
thinking *and* text *and* a tool call; a signature that can answer with at most one event drops the
rest silently. The honest half: **every assistant message in every probe capture on disk carries
exactly one block** (54 messages, 54 blocks — 23 thinking, 16 tool_use, 15 text), so the narrower
signature would have looked correct on this evidence and would have been wrong against the vendor's
own type. The two extra parameters are the injected counter (an unmapped ending is counted, G-M4-5)
and the turn's `tool_use_id → our name` map, which is what lets a tool **result** be attributed to
the call it answers — the engine sends the result back with an id and no name.

**The projection moved to `master/projection.py`** because `sdk_master.py` reached 652 lines and
`tests/boundaries/test_composition_root.py::test_no_source_file_exceeds_600_lines` went red. The seam
it fell on is the right one: one module knows the engine's *shapes* and is pure, the other knows its
*lifecycle* and holds the client. The pure half is what can be driven over every recorded stream on
disk, which is a stronger test than any live turn (a live turn shows the shapes that happened to
occur in it).

## T21-5 · One client per turn, and the two things that forced it

Not a preference. `send()` is an `AsyncIterator` (§6:472, DP12) and the turn driver owns **one event
loop per turn** on a worker thread it tears down with the turn; a vendor client is bound to the loop
it connected on. The contract suite proves the same thing from the other side: `stream()` wraps each
turn in its own `asyncio.run`, so two `send()` calls on one runtime are two loops. A client held
across turns is a client held across loops.

Three consequences, each of which changed a design decision:

* **`resume()` cannot mutate in place, and does not have to.** Between turns there is no live
  connection, so `resume()` records the id and the next turn opens on it — which is exactly DP9's
  *"each resume is a new subprocess"*, arrived at by necessity rather than by discipline.
* **`interrupt()` cannot await the engine.** It is called from the driver's thread *and* from inside
  the consuming loop (the contract row issues it from the `async for` body), so a blocking wait from
  the second would deadlock on the loop it is waiting for. It schedules the vendor's `interrupt()`
  with `run_coroutine_threadsafe` and the turn's teardown reaps it on a **bounded** wait.
* **The turn ends when we say it ended.** After an interrupt this runtime stops projecting and writes
  its own terminal event rather than relaying whatever the engine had already buffered. Without it,
  "the turn stopped" would depend on how much the vendor's reader had pulled ahead — a race the
  contract's `interrupt_during_a_turn_stops_it` row would sometimes pass. P2 is the justification:
  the engine's own result for an interrupted turn arrives later and is nobody's answer by then.

## T21-6 · Two ids, because the engine has two — measured, not assumed

`conversation_id()` answers *"which conversation am I continuing"* and is stable across turns.
`MASTER_SESSION_KEY` on each event's payload answers *"which engine session"* and is what the turn
driver persists (`orchestration/master_turn.py` reads it off the payload; D10).

**They cannot be the same field, and the capture is why.** `docs/probes/2026-09-14-schemas/
agent-sdk-mcp/captures/resume/raw-stream.jsonl` shows a resumed conversation coming back under a
**new** `session_id` (`081dd12b-…` before, `e6fed1a4-…` after). So a runtime reporting the engine's
session id as its identity would report a *different* identity after every resume, and the contract's
`resume_keeps_the_conversation_identity` row — `None` → id → **still** id after a turn — could not be
satisfied by any correct engine implementation. T18 §T18-7.3 said the plan reads as though the seam
answers that row and that T21 supplies the engine's channel; this is the channel, and this is why it
is not the obvious field.

`MASTER_SESSION_KEY` is spelled in two modules (here and in `orchestration/master_turn.py`) because
`orchestration/` is L3 and `master/` is L5, so the import would be upward (§5.0).
`test_the_session_key_has_one_spelling` compares them and goes red on divergence — §T4-3's repair,
reused.
